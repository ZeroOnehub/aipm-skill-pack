# 评测体检

> 改编自 [hamelsmu/evals-skills](https://github.com/hamelsmu/evals-skills) 的 `eval-audit`（MIT，Hamel Husain）。改动：中文化；名字改为 `eval-audit`；引用的同仓库 skill 名换成本合集里的名字；产出物默认存进拾阶的评测目录。

检查一套 AI 评测流程，输出按优先级排序的问题清单和具体的下一步。

## 总览

1. 收集评测材料：轨迹、评估器配置、评委提示词、标注数据、指标看板
2. 按六个方面逐项诊断
3. 按影响排序写报告，每个问题都配修法

## 前提

能拿到评测材料：通过可观测性工具（Phoenix、Braintrust、LangSmith 等，有对应 MCP 就用）或本地文件（CSV、JSON 轨迹导出、notebook、评测脚本）。什么都没有就直接跳到「没有评测体系」。

## 诊断

逐项检查，看材料确认问题是否存在，存在就记下来。按对产品的影响排序，最重要的放最前。

### 1. 错误分析

**查：有没有在真实或合成轨迹上做过系统的错误分析？**

找：标注过的轨迹集、失败类别定义、阅读轨迹的笔记。有评估器但没有成文的失败类别，多半跳过了错误分析。

**缺失时：** 没做错误分析就建的评估器，测的是「有用性」「连贯性」这种泛泛的东西，不是真实的失败。从 `eval-error-analysis` 开始；没有轨迹就先用 `eval-synthetic-data`。

参考：[Your AI Product Needs Evals](https://hamel.dev/blog/posts/evals/index.html)、[LLM Evals FAQ](https://hamel.dev/blog/posts/evals-faq/)

**查：失败类别是想出来的，还是看出来的？**

从论文借来的通用标签（「幻觉分」「毒性」「连贯性」）说明是头脑风暴出来的；贴着产品的类别（「漏掉查询约束」「对客户语气不对」「编造房源配置」）说明是看出来的。

**想出来的时：** 通用类别会漏掉产品特有的失败，评估器纸面分数好看却抓不到真问题。从轨迹出发，用 `eval-error-analysis` 重做。

参考：[Who Validates the Validators?](https://arxiv.org/abs/2404.12272)

### 2. 评估器设计

**查：评估器是不是二元的通过 / 失败？** 标出所有用 1～5 分、字母等级、或没有明确及格线的数字分的。

**不是二元时：** 分级量表很难校准，标注员说不清 3 分和 4 分差在哪，评委会继承这些噪声。改成有明确定义的通过 / 失败，用 `eval-judge-prompt`。

参考：[Creating an LLM Judge That Drives Business Results](https://hamel.dev/blog/posts/llm-judge/)

**查：评委提示词是否针对一种具体失败？** 标出所有整体打分的（「这个回答有帮助吗」「评价输出质量」）。

**太笼统时：** 整体评判的结论没法指导行动。一个评委只查一种失败，配明确的通过 / 失败定义和示例。用 `eval-judge-prompt`。

**查：能用代码查的有没有用代码？** 标出用大模型评委查客观标准的：格式校验、约束满足、关键词、Schema。

**过度依赖评委时：** 客观检查换成代码（正则、解析、Schema 校验、执行测试），评委只留给需要判断的标准。

**查：有没有拿相似度指标当主要评测？** 标出用 ROUGE、BERTScore、余弦相似度、embedding 距离当生成质量主评估的。

**存在时：** 这些指标测的是表面重合，不是正确性。适合检索排序，不适合评生成。换成基于具体失败的二元评估器。

### 3. 评委校准

**查：大模型评委有没有和人工标签对过？** 找混淆矩阵、TPR / TNR、一致性分数。线上在用的评委却没有校准数据，是严重问题。

**没校准时：** 没校准的评委可能一直漏掉失败或误伤通过的。在留出的测试集上测 TPR 和 TNR，用 `eval-validate-judge`。

**查：一致性是用 TPR / TNR 测的，还是用原始准确率？** 标出用「准确率」「一致百分比」或 Cohen's Kappa 当主指标的。

**用准确率时：** 类别不平衡时原始准确率会误导：90% 都通过时，一个永远说通过的评委准确率 90%，却一个失败都没抓到。用 TPR 和 TNR，它们直接对应偏差修正。用 `eval-validate-judge`。

**查：有没有正确切分训练 / 开发 / 测试？** 检查评委提示词里的示例，是不是和测评委表现的数据是同一批。

**泄露时：** 用评测数据当示例会虚高一致性、掩盖评委的真实错误。切成训练（示例来源）、开发（迭代）、测试（最终测量）。用 `eval-validate-judge`。

### 4. 人工审核流程

**查：谁在看轨迹？** 是业务专家还是外包标注员。

**外包且不懂业务时：** 普通标注员能发现格式错误，但会漏掉专业失败（药物剂量错、法条引错、房源配置对不上）。要让业务专家参与。

参考：[A Field Guide to Improving AI Products](https://hamel.dev/blog/posts/field-guide/)

**查：审核的人看的是完整轨迹，还是只有最终输出？**

**只看输出时：** 看不出流程在哪一步断的。要展示完整轨迹：输入、中间步骤、工具调用、检索资料、最终输出。

**查：数据是怎么呈现给审核者的？** 标出原始 JSON、未排版的文本、单元格里塞着轨迹的表格。

**原始格式时：** 审核者把精力花在解析数据上，而不是判断质量。按自然形式呈现：渲染 Markdown、代码高亮、表格就画成表格。用 `eval-review-ui`。

### 5. 标注数据

**查：标注数据够不够？** 错误分析约 100 条轨迹达到饱和；评委校准需要约 50 条通过、50 条失败。数据少时，用更好的抽样补：
- **随机**：永远保留一部分随机样本，用来发现未知问题。
- **聚类**：按语义相似度分组，每组看代表性的。
- **数据分析**：看延迟、轮次、工具调用、token 的统计离群值。
- **分类**：用已有评估、预测模型或大模型筛出可疑轨迹，谨慎使用。
- **反馈**：用用户的明确反馈（投诉、点踩）筛轨迹。

**不够时：** 小数据集算出的失败率不可靠、置信区间很宽。用上面的抽样方法收集更多标注，或用 `eval-synthetic-data` 补充。

### 6. 流程维护

**查：大改之后有没有重做错误分析？** 看最近一次错误分析和换模型、改提示词、加功能、线上事故的先后。

**过期时：** 流程变了，失败模式也会变，为旧流程建的评估器会漏掉新失败。每次大改后都重做错误分析。

**查：评估器有没有人维护？** 找定期重新校准评委、更新评测集的记录。

**建完就不管时：** 流程演进，评估器会慢慢失效。定期用新的人工标签重新校准评委，按当前真实使用情况更新评测集。

## 没有评测体系

如果什么评测材料都没有（没有轨迹、没有评估器、没有标注）：

1. 先用 `eval-error-analysis` 分析一批真实轨迹。
2. 没有线上数据就用 `eval-synthetic-data` 造测试输入，跑完整条流程，再做错误分析。
3. 错误分析做完之前，不建议搭评估器、评委或看板。

## 报告格式

按影响排序，每条：

```
### [问题标题]
**状态：** [存在问题 / 正常 / 无法判断]
[一两句话说明发现的具体问题]
**修法：** [具体动作，引用对应的 skill 或文章]
```

按六个方面分组，没发现问题的方面省略。

## 反模式

- 不看实际材料，当成检查清单走一遍。
- 给出和对方流程无关的泛泛建议。
- 错误分析没做完就推荐建评估器。
- 能用代码检查的失败却建议上大模型评委。
- 只体检一次。大改之后要重新体检。
