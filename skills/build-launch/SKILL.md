# 研发交接、同步交接与上线检查

## 两句总纲

- **交接 ＝ 让写代码的人不用猜。** 会改变范围、成本、安全、隐私的事，开工前定下来；其余给默认值并写明理由。
- **上线 ＝ 证据齐了再放人进来。** 是否表有一个「否」就不上线；没有真实 Key、没跑过真实模型的写「待验」，不写「是」。

先问用户这次做哪件事：**研发交接**、**同步交接**还是**上线检查**。从总控进来时按站名判断，不用再问。下文「本 skill 目录」指这份 SKILL.md 所在的文件夹。

## 拾阶和开发文件夹怎么分工

- **拾阶工作区只放文档，不写产品代码。** 代码在单独的**开发文件夹**，默认 `~/Documents/project/AI Workbench/开发/`。一个开发文件夹可以放多个产品，每个产品一个 `projects/<产品名>/`，所有产品共用一套规则卡、手册和 `verify.sh`，上线时也共用一个腾讯云免费环境。
- 开发文件夹里，编码 AI（Claude Code、Codex、Pi 等）照规则卡 `AGENTS.md` 走六个阶段：0 PRD 体检（在拾阶做完）→ 1 技术适配 → 2 后端 MVP → 3 正式前端 → 4 上线 → 5 收尾。每个阶段交证据包，测试、密钥、重启恢复、前端构建、文件齐全五项由 `verify.sh` 判。
- 拾阶通过 `aipm.json` 的 `build` 字段记住产品在哪（格式见 `aipm-hub` 的 references/aipm-json.md），项目面板直接读那边的进度和证据。

## 模式一：研发交接（04 阶段第 03 站）

### 输入

`02-PRD/PRD.md`、`04-AI方案设计/架构方案.md`（尤其第 13 节待确认清单里的「研发判断」）、`04-AI方案设计/系统提示词-v*.md`、`05-评测/可行性小样/小样结论.md`（有哪个读哪个），以及 `aipm.json` 里已经 `resolved` 的决定（不再重复问）。

### 1. 研发视角的 PRD 体检

对照 [templates/研发PRD.md](templates/研发PRD.md) 的 8 个字段逐项检查，每项标「清楚 / 含糊 / 缺失」，然后把缺口分两类：

- **必须问**：会改变目标用户、核心任务、成本、安全、隐私或交付范围的。常见的有：效果标准完全缺失；没说是否涉及个人信息或企业机密；没说模型和成本上限；主链路是一次生成还是分步确认没说清；上线是内部试用还是对外公开；内容或数据谁来维护、用什么维护。
- **可默认**：其余。先填默认值并写理由，让用户确认一次。

**上线套餐（D9）每次都要定**：默认上线到腾讯云开发，个人实名认证就能用。问一次「免费体验版还是个人版？免费体验版 0 元，一次 6 个月可续，每月 3000 资源点，用完即停不欠费；个人版 19.9 元/月，每月 4 万资源点。推荐先用免费体验版。」**先看开发文件夹里别的产品**：`projects/*/docs/项目状态.md` 的「线上资源」写了环境 ID 的，说明已经有环境，D9 不问，直接记「复用已有环境（与 XX 共用额度和到期日）」：一个腾讯云账号只送一个免费环境。

**专门找技术上互相矛盾的要求**，这是产品经理最容易漏、研发最先撞上的：

| 常见矛盾 | 例子 | 一般怎么裁 |
|---|---|---|
| 时延要求 vs 输出长度 | 「5 秒内返回」但一次要写三段带理由的方案 | 改成「5 秒内出现第一条，其余流式补齐」 |
| 指标 vs 采集能力 | 「到店率」但没有登录、没有订座，采集不到 | 换成能采集的代理指标，或者补埋点和账号 |
| 质量门槛 vs 没有定义 | 「人工抽检合格率 ≥90%」但没写什么叫合格 | 记为「待样例打分」（见下文） |
| 隐私承诺 vs 功能 | 「不保存会话」但要「继续上次」 | 存在浏览器本地，或者改承诺 |
| 成本上限 vs 用量和模型 | 月预算 300 元，但每次要调 3 次大模型 | 算出单次成本再定 |

### 2. 出《研发补全清单》

写进 `04-AI方案设计/研发交接包/研发补全清单.md`：

```markdown
# PRD 补全清单

## 必须问（本轮不超过 5 个）
### 问题 1：{一句话}
- 为什么重要：
- 选项：A / B / C
- 推荐：{哪个，一句理由}
- 不选的后果：

## 可默认（已用默认值填上，请确认）
| 缺口 | 默认值 | 理由 |

## 已发现的矛盾
- 矛盾点 / 推荐裁决
```

每个必须问的问题同时写进 `aipm.json` 的 `pending`（`kind: decision`，`stage: ai-design`，`text` 写问题，`recommend` 写推荐，`source` 指向这份清单）。用户在面板上点「去处理」或者直接回复「按推荐」都可以。还有没关的就再来一轮，每轮仍不超过 5 个。**清单全部关闭才往下走**：编码 AI 会把它当成阶段 0 的结论，不会再问一遍。

**效果标准写不出来时不要逼用户写数字**，记为「待样例打分」：第一次用真实模型跑通时，拿 5～10 条真实样例，按产品类型给不超过 5 个维度、每个 1～3 分的评分表让用户打分，再据此写标准。默认维度：

| 产品类型 | 默认维度 |
|---|---|
| 写作 / 生成 | 覆盖要求、结构合规、语言质量、事实无误、长度合适 |
| 问答 / 知识库 | 回答正确、引用来源、不编造、简洁、拒答边界 |
| 推荐 / 匹配 | 符合约束、理由可信、不推荐库外对象、多样性 |
| 分析 / 数据 | 结论正确、数据引用准确、推理可追溯、格式合规 |

### 3. 写交接包（拾阶这边的记录）

清单关闭后，在 `04-AI方案设计/研发交接包/` 写这四份：

```
研发交接包/
├── 交接说明.md
├── 研发补全清单.md
└── docs/
    ├── PRD/PRD.md       ← 研发 PRD
    └── 项目状态.md       ← 决策台账
```

1. **`docs/PRD/PRD.md`**：按 [templates/研发PRD.md](templates/研发PRD.md) 的 8 个字段，从拾阶的 PRD、架构方案和已拍板的决定里**提炼**，不是复制。写代码的人只看这一份就能开工。
2. **`docs/项目状态.md`**：按 [templates/项目状态.md](templates/项目状态.md) 写决策台账（不超过 10 项），已定的写结论和依据（指向拾阶里的哪份文档），没定的写「待定」和谁来定。「当前阶段」那四行照模板写，不要改写法，面板要读。
3. **`交接说明.md`**，写清这几件事：
   - 一句话：这是什么产品，第一版做到哪；
   - 谁来写代码：产品经理自己用编码 AI，还是研发团队；
   - 代码文件夹在哪，怎么开工：用编码 AI 打开**开发文件夹**（`AGENTS.md` 所在那一层），发送「请读取项目根目录的 AGENTS.md，按其中"启动流程"开始。继续做 <产品名>。」；
   - 第一版要做的组件（架构方案里「必选」的）、以后再做的（「二期」）、取决于问题回答的（「待确认」）；不是 Agent 形态的写「固定流水线 / 单次调用，不用 Agent 组件」；
   - 技术待定项：架构方案第 13 节「研发判断」原样列出，由编码 AI 或研发判断；
   - 每个开发阶段结束要拿回什么：证据包（截图、照着做清单、是否表、`verify-输出.txt`），有「否」就不算完成；
   - 做出来以后回拾阶做什么：05 评测用 MVP 的真实输出，06 上线检查用本 skill 的模式三；
   - 有新需求时：先回拾阶升版，再同步交接，不要直接让编码 AI 改。

### 4. 放进开发文件夹

这一步会在拾阶工作区**以外**写文件，先用一个问题问清（推荐项放第一个）：

- 开发文件夹放哪：默认 `~/Documents/project/AI Workbench/开发/`；产品文件夹是 `projects/<项目名>/`；
- 谁来写代码：自己用编码 AI（Claude Code / Codex / Pi）/ 研发团队。研发团队写代码时也照样放，规则卡和手册给他们参考。

用户确认后运行：

```bash
python3 <本 skill 目录>/scripts/install_kit.py --kit "<开发文件夹>" --name "<项目名>" --project "<项目根目录>"
```

脚本会：第一次建开发文件夹（规则卡、`CLAUDE.md`、三份手册、PRD 模板、`verify.sh`，并 `git init`），已有的只补缺的文件、改过的不覆盖；建产品文件夹，放进研发 PRD、决策台账、补全清单、阶段 0 是否表；把交接说明、架构方案、系统提示词、PRD 原文、迭代记录放进 `docs/拾阶交接/`；按 `architecture-features.json` 的选型复制「必选」组件的说明和参考代码；最后跑一次 `./verify.sh <项目名> 阶段0`。

- verify 有「不通过」时按输出修好再跑，不要带着「否」交出去。
- 脚本最后打印的 `build` 字段写进 `aipm.json`（再加上 `"tool"`：用户选的写代码方式）。

### 5. 收尾

更新 `aipm.json`：04 阶段第 03 站「研发交接」记 `passed`（有待定项时记 `passed_pending`，`note` 写还差什么）。告诉用户：

1. 代码文件夹在哪，开工发哪句话（照抄交接说明）；
2. 项目面板上会多一张「研发进度」卡，显示编码 AI 做到哪个阶段、是否表有没有「否」；
3. 最先要并行去办的事（例如注册腾讯云并实名、法务确认合规口径）。

## 模式二：同步交接（开发中途升版后）

`aipm.json` 里有 `build`，PRD 或架构方案又升了版（通常是 `agent-architecture` 的升版模式结束时提示过来）：

1. **研发 PRD 跟着改**：按新版 PRD 和架构方案更新 `研发交接包/docs/PRD/PRD.md`，开头的来源行写新版本号和日期；新增、改动的地方标「v<新版本> 新增 / 修改」。
2. **交接说明加一节「本次同步」**：新需求一句话、选型变化（照抄 `04-AI方案设计/迭代记录.md` 最新一条）、骨架待办、新拍板的决定。
3. 运行：

   ```bash
   python3 <本 skill 目录>/scripts/install_kit.py --kit "<build.kit>" --name "<build.name>" --project "<项目根目录>" --sync
   ```

   旧版研发 PRD 会存进 `docs/PRD/历史/`；`docs/拾阶交接/` 整体刷新，新选中的组件补进参考代码。脚本**不碰**编码 AI 维护的 `docs/项目状态.md`。
4. 告诉用户回编码 AI 说：「拾阶同步了新版本，读 docs/拾阶交接/迭代记录.md 最新一条，按骨架待办增量修改。新拍板的决定记进决策台账。」
5. `aipm.json` 的 `build` 加 `"synced": "<日期>"`。

## 模式三：上线检查（06 阶段第 01 站）

上线**之前**做。产物写进 `06-上线复盘/上线检查-<版本>.md`，模板见 [templates/上线检查.md](templates/上线检查.md)。

### 0. 先读研发轨道的证据

`aipm.json` 有 `build` 时，先读 `<build.path>` 下面这些：`docs/项目状态.md`（当前阶段、线上资源、访问地址）、`docs/阶段文档/上线方案摘要.md`、`docs/evidence/阶段4/` 的是否表和 `verify-输出.txt`。开发还没走完阶段 4（部署手册第六部分的验收清单没过），上线检查直接记 `blocked`，`note` 写「研发还在阶段 N」。下面是否表的第 2～6、12 项优先引用这些证据的路径。

没有 `build`（研发团队在别处开发）时，让研发交回同样的证据包，存进 `06-上线复盘/上线证据/`。

### 1. 埋点方案

对 PRD 里的每个指标，写清它靠哪个事件算出来：事件名（表达业务行为，如 `plan_shown`、`plan_saved`、`feedback_reported`）、什么时候触发、带哪些属性、分子分母怎么算。**算不出来的指标**要么补埋点，要么换代理指标，要么从 PRD 删掉，三选一，写进 `pending` 让用户拍板。埋点不能阻塞核心操作，不上传用户完整输入和私密内容。

### 2. 灰度与回滚

- 先给谁用：邀请码、白名单、按比例，人数多少；
- 观察哪几个数、看多久；
- 回滚条件：直接用 PRD 的停止条件，写成「出现 X 就关闭入口 / 切回旧版」，并写清谁有权限执行。

### 3. 上线是否表

逐项填「是 / 否 / 待验」，并写证据在哪（截图、地址、文档、开发文件夹里的证据路径）。**任何一项是「否」就不上线；「待验」要写清什么时候、由谁验。**

| # | 检查项 |
|---|---|
| 1 | 05 评测结论满足 PRD 的上线条件（附 `05-评测/评测结论.md`） |
| 2 | 用真实模型跑通了每条核心链路，记录了模型、时延、成本（不是 mock） |
| 3 | 密钥不在代码仓库、前端和日志里（`verify.sh` 第 5 项） |
| 4 | 服务重启后数据还在，实际验证过（`verify.sh` 第 6 项） |
| 5 | 有账号的产品：A 用户看不到 B 用户的数据，权限在后端判断 |
| 6 | 错误不暴露技术细节，模型失败、超时有兜底页面 |
| 7 | 埋点已上线并能看到数据，每个上线指标都能算出来 |
| 8 | 灰度范围和回滚开关已就绪，知道谁来执行 |
| 9 | 合规已确认：面向公众提供生成式 AI 服务时的备案或登记、内容安全；行业规则（如酒类、医疗、金融、未成年人）；用户协议和隐私政策。由法务或负责人确认，AI 只列清单不下结论 |
| 10 | 费用已告知并确认：模型和云资源的月费用量级、超限时怎么办 |
| 11 | 用户反馈渠道已就绪（产品内反馈、群、工单），有人负责看 |
| 12 | 手机和电脑都走过一遍核心流程 |

### 4. 收尾

全部「是」（或「待验」已有明确的验证人和时间）后，06 阶段第 01 站记 `passed`，告诉用户可以按灰度计划上线，并提醒上线后约定的时间点回来做指标复盘（`metrics-review`）。有「否」时站记 `blocked`，`note` 写卡在哪一项。

## 红线

1. 必须问的问题一次超过 5 个，或者问题不带推荐答案。
2. 用默认值悄悄填掉会改变范围、成本、安全、隐私的缺口。
3. 把 mock 结果、没跑过的验证写成「是」。
4. 是否表有「否」还建议上线。
5. 合规项替法务下结论。
6. 在拾阶的项目目录里写产品代码；没问过用户就往工作区以外写文件。
7. 同步交接时覆盖编码 AI 维护的 `docs/项目状态.md`，或者让编码 AI 整体重写代码。
