# 做标注工具

> 改编自 [hamelsmu/evals-skills](https://github.com/hamelsmu/evals-skills) 的 `build-review-interface`（MIT，Hamel Husain）。改动：中文化；名字改为 `eval-review-ui`；产出物默认存进拾阶的评测目录。

## 总览

做一个 HTML 页面：从数据文件（JSON / CSV）加载轨迹，一次显示一条，有通过 / 失败按钮、自由备注框、上一条 / 下一条导航，标注存到本地文件（CSV / SQLite / JSON）。然后按下面的原则贴合业务定制。

## 数据呈现

所有数据都用这个领域最易读的形式呈现：邮件像邮件，代码有语法高亮，Markdown 要渲染，表格画成表格，JSON 格式化并可折叠。

- **折叠重复内容。** 每条轨迹都有同样的系统提示词，就放进 `<details>` 折叠。
- **提取关键元数据。** 轨迹里埋着房源名、客户类型、会话 ID 这类信息，提出来放在标题或标签里显眼展示。
- **按角色或状态配色。** 用左边框颜色区分用户消息、助手消息、工具调用和系统提示词，一眼能分清。
- **相关元素视觉上成组。** 工具调用和它的返回要连在一起（缩进、共用边框）。
- **不帮助判断的内容折叠起来。** 冗长的工具返回 JSON、中间推理、调试信息默认折叠。
- **突出最重要的。** 审核者要判断的主内容视觉上最显眼。关键实体加粗（价格、日期、人名），用字号和间距建立层级。
- **展示完整轨迹。** 包括所有中间步骤（工具调用、检索资料、推理），不只最终输出。默认折叠，但随时能展开。
- **渲染前做清洗。** 渲染模型输出前去掉原始 HTML；Markdown 里的图片可能是追踪像素，必要时禁用。

## 收集反馈

在轨迹层面标注：审核者判断整条轨迹，不是单个片段。

- 主操作是二元的通过 / 失败按钮。
- 自由备注框，让审核者写清哪里错了（或哪里对了）。
- 「稍后」按钮，给拿不准的情况。
- 每次操作自动保存。

等错误分析定出失败类别以后，可以再加预设的失败类别（复选框、下拉或选择列表），让审核者在写备注之外直接选。**首版不要加。**

## 导航和状态

- 上一条 / 下一条按钮，方向键也能翻。
- 进度计数（「还剩 87 条中的 12 条」）。
- 按 ID 跳到指定轨迹。
- 已标 / 未标的数量。

## 快捷键

```
方向键 = 翻页
1 = 通过          2 = 失败
D = 稍后          U = 撤销上一步
Cmd+S = 保存      Cmd+Enter = 保存并下一条
```

## 加载哪些轨迹

工具要能从任意来源（JSON / CSV 文件）加载轨迹。抽样逻辑放在工具外面单独写脚本，先从随机抽样开始。

## 可选功能

- **参考面板**：可开关的侧栏，显示标准答案、期望回答或评分标准。
- **筛选**：按和产品相关的元数据筛（渠道、用户类型、流程版本）。
- **聚类**：按元数据或语义相似度分组，每组展示代表性轨迹，可下钻。

## 设计检查清单

- [ ] 每条轨迹的布局、控件和用词都一样
- [ ] 通过和失败按钮视觉上明显不同（颜色、大小）
- [ ] 所有主操作都有快捷键
- [ ] 折叠后仍能看到完整轨迹
- [ ] 标注自动保存，不需要手动点保存
- [ ] 默认按整条轨迹标注，不按片段
- [ ] 所有数据按原生形式渲染（Markdown 渲染成 HTML、代码高亮、JSON 格式化、表格画成表格、链接可点击）

## 测试

做完后用 Playwright 验证。

**视觉检查**：加载有代表性的数据后截图，检查：
- 布局和间距：层级清楚吗？能一眼看到重点吗？
- 可读性：所有数据都按原生形式渲染了吗？有没有原始 JSON、没渲染的 Markdown、没样式的内容？
- 美观：看起来专业、干净吗？业务专家愿意用吗？
- 响应式：不同窗口大小下布局稳不稳？

**功能测试**：写一个 Playwright 脚本走完整个标注流程：
1. 打开工具，确认轨迹显示出来
2. 点通过，确认标注已保存
3. 点失败并写备注，确认两者都保存了
4. 点稍后，确认被记录
5. 用按钮和快捷键前后翻页
6. 确认进度计数正确更新
7. 刷新页面，确认标注还在（自动保存生效）
8. 展开折叠区域（系统提示词、工具调用），确认内容能看到
9. 逐个测试快捷键是否触发正确的操作

没有浏览器工具时，说清哪些检查没做。
