# 错误分析

> 改编自 [hamelsmu/evals-skills](https://github.com/hamelsmu/evals-skills) 的 `error-analysis`（MIT，Hamel Husain，配套课程「AI Evals For Engineers & PMs」）。改动：中文化；示例改成中文场景；名字统一加 `eval-` 前缀；产出物默认存进拾阶的评测目录。

带用户阅读 AI 系统的运行轨迹，建一份「系统是怎么失败的」清单。

## 总览

1. 收集约 100 条有代表性的轨迹
2. 逐条阅读，判通过 / 失败，记下哪里出错
3. 把相似的失败归类
4. 用这些类别给每条轨迹打标签
5. 算各类失败率，决定先修什么

## 流程

### 第 1 步：收集轨迹

记录完整轨迹：输入、每一次模型调用、工具调用、检索到的文档、推理步骤、最终输出。

**目标约 100 条。** 大约到这个量，新轨迹就不太会暴露新的失败类型了，具体看系统复杂度。

**优先用真实用户数据：**
- 量小：随机抽样
- 量大：按关键维度分层抽（问题类型、用户群、功能模块）
- 可以用 embedding 聚类（K-means）保证多样性

**真实数据太少时用合成数据：**
- 用 `eval-synthetic-data` 生成测试输入
- 让合成输入跑完整条流程，记下完整轨迹

### 第 2 步：读轨迹，记笔记

把每条轨迹给用户看，只问一个问题：**这次结果好不好？** 通过还是失败。

失败的记下哪里出了错。只记**轨迹里第一个出错的地方**：错误会连锁，根因修了，下游症状自然消失。一条轨迹里不必追每个问题。

写观察，不写解释。写「SQL 漏了预算条件」，不写「模型大概没理解预算」。

**记录模板：**

```
| 轨迹 ID | 轨迹 | 哪里出错 | 通过/失败 |
|---|---|---|---|
| 001 | [完整轨迹] | 漏了筛选条件：用户要求「能带宠物」被忽略 | 失败 |
| 002 | [完整轨迹] | 日程冲突了还推荐那个时间 | 失败 |
| 003 | [完整轨迹] | 对高端客户用了很随意的语气；房型推错 | 失败 |
| 004 | [完整轨迹] | - | 通过 |
```

**要点：**
- **不要**一开始就拿着预设的失败清单。类别要从用户实际看到的问题里长出来。
- 用户说不清哪里不对时，可以用常见类型提示：编造事实、格式错误、忽略用户要求、语气不对、工具用错。

### 第 3 步：把失败归类

看完 30～50 条后就开始归类，不用等 100 条看完。早归类能帮你在后面的轨迹里看得更准。类别会不断演化，目标是名字具体、能指导行动，不求完美。

1. 通读所有失败笔记
2. 相似的归到一起
3. 看着像、但根因不同的拆开
4. 每类起一个清楚的名字，配一句定义

**什么时候拆，什么时候合：**

要拆（根因不同）：
- 「编造了房子的配置（太阳能板）」和「编造了客户的行为（安排了客户没要求的看房）」：一个编造外部事实，一个编造用户意图。

要合（根因相同）：
- 「漏了卧室数筛选」+「漏了宠物筛选」+「漏了价格区间筛选」→ **漏掉查询约束**

**让大模型帮忙聚类**（用户亲自看过 30～50 条之后才用）：

```
下面是阅读 AI 系统轨迹时记下的失败标注。
请把相似的失败归成 5～10 个不同类别。
每个类别给出：
- 清楚的名字
- 一句话定义
- 哪些标注属于它

标注：
[粘贴标注]
```

大模型给的分组一定要和用户一起过一遍。大模型容易按字面相似归类（比如因为都提到「登录」，就把「应用崩溃」和「登录慢」放在一起）。

**目标 5～10 个类别**，要求：
- 互不重叠（每个失败只属于一类）
- 定义清楚到别人也能一致地使用
- 可行动（每类都指向一个具体的修法）

### 第 4 步：给每条轨迹打标签

回到所有轨迹，按每个失败类别打二元标签（是 / 否）。每条轨迹每个类别一列。工具随用户习惯：表格、标注工具（见 `eval-review-ui`）、或者一个简单脚本。

### 第 5 步：算失败率

```python
failure_rates = labeled_df[failure_columns].sum() / len(labeled_df)
failure_rates.sort_values(ascending=False)
```

最常见的失败类别就是最先要处理的。

### 第 6 步：决定每类失败怎么处理

按这个顺序和用户逐类过：

**能不能直接修？** 很多失败有明显的修法，根本不需要评估器：
- 提示词里压根没提这个要求。例：邮件里从不附房源照片链接，因为提示词从没要求。加上这条指令。
- 缺工具或工具配置错了。例：用户想改约，但没有给模型改约的工具。加上工具。
- 检索、解析、集成里的工程 bug。修代码。

能直接修好的先修。只有修完还在的失败，才考虑做评估器。

**评估器值不值得做？** 不是每个剩下的失败都需要评估器，搭建和维护都有成本。问用户：
- 这个失败出现得够不够频繁？
- 出现时业务影响多大？一个罕见但会造成收入损失的失败，可能比一个常见但只是烦人的失败更重要。
- 这个评估器真的会被用来反复迭代系统吗，还是走形式？

评估器留给用户会反复迭代的失败，从频率最高、影响最大的类别开始。

**确实需要评估器的：** 客观的东西优先用代码检查（正则、解析、Schema 校验）。只有需要判断的才用 `eval-judge-prompt` 写大模型评委。关键要求（安全、合规）即使已经改了提示词，也可以留一个评估器当护栏。

### 第 7 步：迭代

一般要来回两三轮。每轮之后：
- 合并重叠的类别
- 拆开太宽的类别
- 把用户会犹豫的定义说得更清楚
- 用新类别重新打标签

## 什么时候停

新轨迹不再暴露新的失败类型时停。大致是：看了约 100 条，最后 20 条没出现新类型。具体看系统复杂度。

## 抽样策略

线上量大时混着用：

| 策略 | 什么时候用 | 做法 |
|---|---|---|
| **随机** | 默认起点 | 从最近的轨迹里均匀抽样 |
| **离群** | 找异常行为 | 按回复长度、延迟、工具调用次数排序，看两端 |
| **失败驱动** | 护栏被触发或用户投诉后 | 优先看被标记的轨迹 |
| **不确定性** | 已经有自动评委时 | 看评委意见不一或置信度低的 |
| **分层** | 保证各用户群都覆盖 | 在每个维度内分别抽 |

## 反模式

- **没看轨迹就先头脑风暴失败类别。** 先读，再归类。
- **从预设类别出发。** 固定清单会带来确认偏差，让类别自己浮现。
- **前期不让用户参与。** 前 30～50 条必须由用户亲自看，类别才扎根于业务知识。
- **用通用分数当类别。** 「幻觉分」「有用性分」「连贯性分」不是从这个产品的真实失败里来的。
- **明显问题还没修就先做评估器。** 先补提示词、补工具、修 bug。
- **只做一次。** 每次大改（新功能、改提示词、换模型、线上事故）后都要重做。
