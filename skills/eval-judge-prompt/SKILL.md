# 写大模型评委提示词

> 改编自 [hamelsmu/evals-skills](https://github.com/hamelsmu/evals-skills) 的 `write-judge-prompt`（MIT，Hamel Husain）。改动：中文化；示例改成中文场景；名字改为 `eval-judge-prompt`；产出物默认存进 AIPM 工坊的评测目录。

为**一种**具体失败设计一个只判通过 / 失败的大模型评委。一个评委只查一件事。

## 前提

- 错误分析做完了，失败类别已经明确（见 `eval-error-analysis`）。
- 这类失败有人工标注的轨迹，至少 20 条通过、20 条失败。
- 代码检查不了这类失败。先把代码手段用尽：很多看起来主观的失败，懂业务以后会发现用关键词、正则或接口调用就能查。例：判断一个 AI 面试教练有没有问「泛泛的问题」（问平时一般怎么做，而不是问过去某一次具体的事），看起来要语义理解，实际上查「通常」「一般」「平时」这类词效果就不错。

## 四个组成部分

每个评委提示词必须有且只有这四部分：

### 1. 任务和评估标准

说清评委评什么。一个评委一种失败。

```
你是一名评估员，判断房产经纪助手写的邮件，语气是否符合客户类型。
```

不要写：「评估这封邮件好不好」或「给邮件质量打 1～5 分」。

### 2. 通过 / 失败的定义

结论严格二元：通过或失败。不用李克特量表，不用字母等级，不给部分分。定义直接来自错误分析里的失败类别说明。

```
## 定义

通过：邮件的沟通风格符合客户类型：
- 高端买家：正式用语，强调稀缺和品质，高端定位，不用随意的口语
- 首次购房者：温暖、鼓励，解释清楚，不用行话，耐心
- 投资客：用数据说话，聚焦回报，有市场分析，简洁专业

失败：语气和客户类型不匹配。例如：
- 对高端买家用「哈喽，这套房超赞的！」这种口语
- 对首次购房者堆满金融术语
- 对投资客用很煽情的语言
```

### 3. 带点评的示例

从人工标注数据里挑通过和失败的例子。

```
## 示例

### 示例 1：通过
客户类型：高端买家
邮件：「尊敬的王先生：很荣幸向您推荐位于滨江一号的一套臻选房源。该物业……」
点评：开头是正式称呼，用词「臻选房源」等符合高端定位，通篇没有口语化表达，语气与高端买家一致。
结论：通过

### 示例 2：失败
客户类型：高端买家
邮件：「哈喽！刚看到一套你可能喜欢的，带泳池啥的，小区也超酷……」
点评：「哈喽！」过于随意，「带泳池啥的」「超酷」是口语，对高端客户不合适，读起来像聊天消息而不是专业沟通。
结论：失败

### 示例 3：通过（边界情况）
客户类型：首次购房者
邮件：「小李你好，我找到一套可能很适合你第一套房的房子。附近学校不错，每月月供和你现在的房租差不多……」
点评：称呼亲切但不过分随意；用「月供和房租差不多」这种好理解的比较来解释，有教育意义又不居高临下；没有「等额本息」「贷款价值比」之类的术语。技术深度不高，但符合首次购房者需要的支持性语气。
结论：通过
```

**挑示例的规则：**
- 至少一个明确通过、一个明确失败、一个边界情况。边界情况最有价值，它教会评委分寸。
- 从训练集里挑（预留 10%～20% 的标注数据专门做这个）。
- 用进提示词的示例必须从开发集和测试集里剔除，否则就是数据泄露。
- 一般 2～4 个示例，4～8 个以后效果就不再提升。

### 4. 结构化输出

用模型服务商的 Schema 约束（如 OpenAI 的 `response_format`、Anthropic 的工具定义，或 DeepSeek 的 JSON 输出模式），或者 Instructor、Outlines 这类库。服务商不支持时，在提示词里写明 JSON Schema。

输出必须**先点评、后结论**。先写点评，逼评委在下结论前把判断说出来。

```json
{
  "critique": "字符串：对照标准对输出做的详细评估",
  "result": "Pass 或 Fail"
}
```

点评要详细，不能三言两语：具体说哪里对、哪里不对，引用输出里的证据。示例里点评写得多细，评委就会写得多细。

## 给评委喂什么

只喂判断所需的信息：

| 失败类型 | 评委需要 |
|---|---|
| 语气不匹配 | 客户类型 + 生成的邮件 |
| 回答不忠实于资料 | 检索到的资料 + 生成的回答 |
| SQL 不正确 | 用户问题 + 生成的 SQL + 表结构 |
| 没遵守指令 | 系统提示词里的规则 + 生成的回复 |
| 工具调用没道理 | 对话历史 + 工具调用 + 工具返回 |

长文档只喂相关片段，不喂全文。

## 选模型

先用能拿到的最强模型。主任务用的模型也可以当评委（评委做的是另一件更窄的事）。确认和人工一致之后再考虑降成本。

## 反模式

- **「有没有帮助」这种模糊标准。** 瞄准错误分析里一个具体、可观察的失败。
- **一个评委评整条轨迹。** 一个评委管多个维度，结论没法指导行动。
- **没有示例。** 没示例，模型不知道在你的产品里什么算失败。
- **用开发集、测试集的数据当示例。** 这是数据泄露，只能用训练集。
- **李克特量表（1～5 分、字母等级）。** 只用通过 / 失败。量表看着精确，实际没法校准：标注的人说不清 3 分和 4 分差在哪，评委也会继承这些噪声。二元判断逼你一开始就定清边界，标注一致性可以测，评委的错也能指导修改。要区分严重程度，就用多个二元评委（例如「事实错误」和「危险的事实错误」），不用一个分级量表。
- **不做校准。** 信任评委之前，用 `eval-validate-judge` 测它和人工的一致性。
- **提示词没修就先做评委。** 如果提示词根本没要求这个行为，先补指令。关键要求可以在修完后留一个评委当回归护栏。
