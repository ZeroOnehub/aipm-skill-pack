# 代码对照验收与存量体检

## 两句总纲

- **静态扫描只给线索，结论要打开代码确认。** 关键词没扫到不等于没实现，扫到也不等于做对了。报告里区分「确认已实现」「确认没实现」和「没扫到，可能在别处」。
- **只读不改。** 这个 skill 只出报告；要改代码，把「先修什么」交给编码 AI 或研发。

先判断这次做哪件事：项目 `aipm.json` 里有 `build`、要检查开发文件夹里的代码 → **对照验收**；用户给了一个别处的项目路径、想看它缺什么 → **存量体检**。下文「本 skill 目录」指这份 SKILL.md 所在的文件夹。

## 模式一：对照验收（05 阶段第 02 站）

### 输入

- 代码：`aipm.json` 的 `build.path`（产品文件夹）。读它的 `docs/项目状态.md`，知道研发做到哪个阶段。研发还没到阶段 2，告诉用户「还没有代码可验」，结束。
- 需求：拾阶的 `02-PRD/PRD.md`（第 8 节验收标准、第 10 节评测样例、第 11 节指标）和代码文件夹里的 `docs/PRD/PRD.md`（研发 PRD）。
- 方案：`04-AI方案设计/架构方案.md`（形态判断、组件选型、工具清单、降级、特征落点）和 `architecture-features.json`。

### 1. 跑自检脚本

在开发文件夹（`build.kit`）里运行 `./verify.sh <build.name>`，**不带阶段名**，这样不会改写证据包。它会跑测试、检查密钥、重启恢复、前端构建，可能要几分钟。把五行汇总抄进报告。

### 2. 静态扫描

```bash
python3 <本 skill 目录>/scripts/scan_project.py "<build.path>" --expect "<项目根目录>/04-AI方案设计/architecture-features.json"
```

- **形态是 Agent**：用 `--expect`，得到按选型对照的组件差距表。
- **形态是固定流水线或单次调用**：**不要**加 `--expect`（方案本来就没选组件，按 Agent 组件对照全是误报）。改成拿方案第 5 节「特征落点」逐条找实现，比如「audit_needed → 输出前拦截」就去找拒答规则和留痕代码。

### 3. 打开代码确认

- 组件差距表里每一条 P0、P1，打开命中位置（或者自己搜）确认，判定写成：**确认已实现**（写文件和行号）/ **确认没实现** / **没扫到，可能在别处**（写清搜了哪些词、看了哪些文件）。
- 工具清单：方案里的每个工具在代码里找到对应的函数或接口，权限（允许 / 需确认 / 禁止）有没有落实。
- 降级策略：工具失败、模型幻觉、超时、越权四种，各找到对应的处理代码。

### 4. 验收标准和评测样例的测试覆盖

PRD 第 8 节的每条 P0 验收标准、第 10 节的每条评测样例，在测试代码里找对应的用例，填表：「有测试（测试名）/ 没测试 / 只能人工验」。「不应发生」的那几条特别看：有没有测试证明它不会发生。

### 5. 写报告

按 [templates/差距报告.md](templates/差距报告.md) 写进 `05-评测/对照验收-<日期>.md`。「先修什么」最多 5 条，按影响排：先是 P0 缺失和「不应发生」没测试的，再是降级缺口。每条写清改什么、为什么、去哪看（`docs/拾阶交接/参考组件/<组件>/README.md`）。

### 6. 收尾

- 「先修什么」里的每一条写进 `aipm.json` 的 `pending`（`kind: gap`，`stage: evaluation`，`source` 指向报告）。
- 问用户要不要把报告复制一份到代码文件夹的 `docs/拾阶交接/对照验收-<日期>.md`，然后让编码 AI 读它，按「先修什么」改。
- 05 阶段第 02 站「对照验收」：没有 P0 缺口记 `passed`；有但用户决定先往下走记 `passed_pending`，`note` 写还差什么。

## 模式二：存量体检（1→N 存量产品，或者任何已有项目）

### 输入

用户给的项目目录。**先确认路径存在、只读**；有 PRD 或需求文档的一起读。

### 1. 扫描

```bash
python3 <本 skill 目录>/scripts/scan_project.py "<项目目录>"
```

读 README、入口文件、配置，再按扫描结果打开命中位置。

### 2. 它现在是什么

六个维度：目标、用户、核心闭环、交付物、边界、约束。每条写结论和证据（README 第几段、哪个文件哪一行）；从代码推出来的标【AI 推断】，推不出来的写「待确认」，不编。

### 3. 它本该有什么

按 `agent-architecture` 的规则做一遍：先判形态（单次调用 / 固定流水线 / Agent）；是 Agent 的，按 prd skill 的 references/Agent特征快问.md 判 14 个特征（证据来自 README 和代码，例如「README 写了会删除文件」→ `destructive_ops` 需要），写成 `architecture-features.json` 放进输出目录，再加 `--expect` 重新扫一次，得到差距表。然后照模式一第 3 步打开代码确认。

### 4. 写两份文件

- **差距报告**：按 [templates/差距报告.md](templates/差距报告.md) 写，「它现在是什么」一节必填。
- **本该有的 PRD**：按 prd skill 的 templates/PRD.md 写精简版草稿，所有内容标出处或【AI 推断】，第 9 节的「Agent 特征判断」表照第 3 步填。用户补全后可以直接当第 02 阶段的输入。

存放位置：在拾阶项目里，放 `01-立项/存量体检/差距报告.md` 和 `01-立项/存量体检/反推PRD.md`；不在拾阶里，放当前目录的 `存量体检-<项目名>/`。

### 5. 收尾

用三行告诉用户：一句话判定（只有雏形 / 基本可用 / 接近可落地）、最该先补的一件事、反推 PRD 里最大的待确认项。在拾阶项目里时，把「先补什么」前 3 条写进 `pending`（`kind: gap`，`stage: initiation`）。

## 红线

1. 改目标项目的任何文件，或者为了验收去运行会删数据、发消息、花钱的命令。
2. 把关键词命中率当成功能完成度，或者没打开代码就写「确认已实现 / 没实现」。
3. 固定流水线或单次调用形态，按 Agent 组件对照出一堆「缺失」。
4. 把 mock 测试通过写成「真实模型验证通过」。
5. 反推的内容不标【AI 推断】，写成事实。
