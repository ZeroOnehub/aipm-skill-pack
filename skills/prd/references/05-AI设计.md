# 第 05 站：AI 设计

**写什么：** 第四节的「全局上下文管理」「Agent 提示词设计」，第七节「兜底策略」。
**回答的问题：** AI 链路由哪几个环节组成，每个环节读什么、做什么、写下什么，出错了系统怎么接住？

这一站写的东西是 05 模型评测的**被测对象**：评测会拿这里的提示词原文去跑题。所以要写到「拿去就能跑」，不能只写意图。

## 1. 先拆链路

把系统处理流程（第 04 站的时序图）里的 AI 部分拆成环节，每个环节一个 Agent（或一次模型调用）。拆的原则：

- **一个环节只有一个职责**：生成和检查分开（写正文的不负责审自己），检查和修改分开（审计只出问题清单，修改交给下游）。
- **下游读上游写下的东西**：一环出错会一路传下去，所以要能单独评测每一环。
- 只有一次调用就能完成的产品（如单轮改写），就是一个环节，不要为拆而拆。

写一张链路表（这张表 05 评测会直接复用为「评测对象」）：

| 环节 | 读什么 | 调什么工具 | 写下什么 | 最怕什么 |
|---|---|---|---|---|
| 大纲 Agent | 用户需求、行业范本、资料 | 行业范本检索、素材扫描 | 大纲、事实基座、术语表 | 事实基座抽错且没人确认 |
| 正文 Agent | 事实基座、前文摘要、本章任务 | 知识库检索、读写记忆 | 章节正文、本章摘要 | 编数字；不照事实基座写 |
| 审计 Agent | 正文、事实基座 | 读记忆 | 问题清单（严重 / 警告 / 提示） | 漏抓；误报 |
| 优化 Agent | 正文、审计清单 | — | 改好的正文 | 改出新错；把待补充编满 |

「最怕什么」一列很重要：它就是后面红线、兜底和评测题目的来源。

## 2. 全局上下文管理

整条链路要共同记住的东西，按**生命周期**分块：

| 区块 | 存什么 | 例子 |
|---|---|---|
| 全局配置 `config` | 整个任务不变的设定 | 标题、领域、文档类型、风格、目标字数 |
| 结构 `structure` | 任务的骨架和进度 | 大纲、当前进行到第几章、总章数 |
| 事实基座 `truth_base` | **经用户确认**的关键事实，审计的唯一可信来源 | 投资总额、技术路线、核心参数 |
| 记忆 `memory` | 已完成部分的压缩，保证前后一致 | 各章摘要、统一术语、上一段结尾 |
| 运行时 `runtime` | 只对当前这一步有用，用完可丢，失败可重用 | 本章检索结果、用户本次的额外要求 |

写法：

1. 给出完整 JSON 结构，字段用英文小写下划线，值写成「说明文字」或示例值。
2. 每块下面一张小表：谁写、谁读、什么时候清空。
3. **事实基座写清来源和确认方式**：「由用户创建任务时填写，或大纲 Agent 从资料中抽取后由用户确认」。没人确认的事实基座是整条链路最大的风险，评测会专门考它。
4. 对话类产品的上下文按「会话 → 用户长期偏好 → 本轮」分块；单次生成类产品可能只有 config 和 runtime，不要硬凑。

## 3. Agent 提示词设计

每个环节先写四行说明，再给提示词全文：

- **职责**：一句话
- **触发**：什么时候调用（用户点击、上一环完成、定时）
- **读 / 写**：读全局上下文的哪些字段，产出写回哪里
- **工具**：工具名、入参、目的、调用时机

提示词全文放在代码块里，固定七段：

```markdown
# Role
你是 {{身份}}。你的核心任务是 {{一句话}}。{{一条最重要的纪律}}。

# Global Context
文档目标：{{config.doc_type}} - {{config.title}}
全局事实：{{truth_base.validated_data}}
前文记忆：{{memory.chapter_summaries}}

# Inputs
本章标题：{{structure.outline[i].title}}
本章关键论点：{{structure.outline[i].key_points}}
用户额外要求：{{runtime.user_requirements}}

# Action Path
1. 意图对齐：……
2. 素材调取：调用 internal_rag_tool 检索……
3. ……

# Tool Use Rules
Tool 1: internal_rag_tool
  入参：query = "当前章节标题 + 关键知识点"
  调用时机：开始写正文前必须先调用

# Output Specifications
{{输出格式。下游要读的一律给 JSON 结构，写明每个字段；给人看的写清结构和长度。}}

# Constraints
- 数据真实性：涉及 truth_base 的数字必须完全一致
- 不编造：资料里没有的写「[待补充：需要××数据]」
- {{本环节的红线}}
```

### 写提示词的八条规矩

1. **变量全部来自全局上下文**，用 `{{区块.字段}}` 引用，和第 2 节的 JSON 字段名一一对应。写完逐个核对，有引用不存在的字段就是错。
2. **Action Path 写成编号步骤**，每步一个动作；需要调工具的步骤写明调哪个工具。
3. **工具规则写入参、目的、时机**，并写「什么时候不要调」（如「检索结果为空时不要再次检索，直接标待补充」）。
4. **输出给程序读的，必须是 JSON**，写明每个字段和取值范围，并写「直接输出 JSON，不要任何开场白」。
5. **不编造的出口要写死**：资料没有时输出什么固定标记（如 `[待补充：需要××数据]`）。没有出口，模型就会编。
6. **约束写成可检查的句子**：「所有章节 suggested_words 之和必须等于 config.target_words」，而不是「字数要合理」。
7. **检查类 Agent 只审不改**，输出问题清单，并给出严重度分级和每条的定位、原文、依据、修改建议。
8. **修改类 Agent 写清不许动什么**：「除审计报告要求修正的之外，关键数字一个符号都不能改动」「待补充标记必须保留」。

提示词里用到的工具，在下面汇总一张工具表（工具名 / 做什么 / 入参 / 返回 / 失败时怎么办），04 技术方案直接照它设计接口。

## 4. 兜底策略（第七节）

三列：触发条件 / 系统行为 / 用户感知。**触发条件要可判定**（有阈值、有错误码），系统行为写降级路径，用户感知写提示原文。

至少覆盖六类：

| 类别 | 例子 |
|---|---|
| 检索不到 / 不可信 | 向量召回 Top10 分数均 < 0.65 → 降级到关键词搜索，并提示「已扩大搜索范围」；仍为空 → 询问是否用通用知识写，并标注来源为通用知识 |
| 模型超时或报错 | 重试 3 次（指数退避），仍失败切备用模型；再失败提示「生成超时，请稍后重试」并给「重新生成」按钮，已生成的部分保留 |
| 输出不合规 | JSON 解析失败或字段缺失 → 带错误信息重试一次；仍失败按段落降级展示，并记录失败日志 |
| 内容越界 | 涉及敏感、违规、超出能力边界的请求 → 固定话术拒答并说明能做什么 |
| 外部依赖失败 | 文档解析失败、第三方接口不可用 → 标记失败项、给出原因和重新上传入口 |
| 成本或用量超限 | 单任务 token 超上限 → 停止生成并提示；月度预算到 80% → 告警给管理员 |

再加上第 1 节链路表「最怕什么」一列里每一项的兜底（如「事实基座没人确认」→ 生成正文前强制弹出确认）。
