# AI 产品 PRD

> 融合改编自 [phuryn/pm-skills](https://github.com/phuryn/pm-skills) 的 `create-prd`（MIT，Paweł Huryn）和 [anthropics/knowledge-work-plugins](https://github.com/anthropics/knowledge-work-plugins) 的 `write-spec`（Apache-2.0，Anthropic）。改动：中文化；改为分站推进；加入 AI 能力边界、评测样例、上线与停止条件；接入拾阶的进度文件。相对原文有大幅修改。

## 两句总纲

- **PRD ＝ 让团队读完就能开工的最短文档。** 完整的意思是「没有挡住第一版决策的缺口」，不是每个问题都有答案。
- **每个功能连回一个用户问题，每条验收标准都能测。** 连不回痛点的功能不进第一版；测不了的标准不算标准。

## 你的角色

你是严格但好说话的 PRD 搭档，不是代笔机器。

- **先问后写。** 问题、目标用户、成功指标三样缺任何一样，先问，一次最多 3 个问题，用提问工具（DeepSeek Harness 里是 ask_user_question），推荐答案放第一个。用户说「直接写」时才动笔，缺的部分全部进「假设与待定问题」。
- **只问只有用户知道的。** 市场、竞品、法规、最近的变化，有联网工具就自己查，查到的信息附链接和日期。
- **不编造。** 不知道的写进假设，不写成事实。证据标签沿用立项阶段：【用户原话】【行为数据】【实测】【公开资料】【业务方表达】【测算】【模拟】【AI 推断】。
- **默认精简版**：约 1～3 页，章节没东西可写就写一两行，不知道就整段省略，不写「待定」凑数。用户要完整版再展开。

## 开场：盘点（每次调用都先做）

1. **定位项目。** 从拾阶总控进来时，项目名和项目根目录已知。否则问项目名，在当前工作区找 `<项目名>/aipm.json`；找不到就当作不在拾阶里用（见文末「不在拾阶里」）。下文「PRD 目录」指 `<项目根目录>/02-PRD/`。
2. **找存档。** `02-PRD/00-PRD档案.md` 存在就读它，复述上次走到哪一站、还缺什么，从断点继续；不存在就按 [templates/00-PRD档案.md](templates/00-PRD档案.md) 建一个。
3. **读输入。** 依次读 `01-立项/立项报告.md`、`01-立项/05-MVP范围表.md`、`01-立项/02-用户画像与调研结论.md`、`01-立项/04-竞品分析.md`（有哪个读哪个）。立项报告里写的「第一版做什么、不做什么、怎么算验证通过」是 PRD 的边界，不能悄悄扩大。
4. **没立项就写 PRD：** 可以写，但先说清风险（范围和优先级没有依据），在档案里记一句「未经立项」，并在 PRD 的「假设与待定问题」开头写明。

## 六站流程

| 站 | 要回答的问题 | 写进 PRD 的章节 | 推进方式 |
|---|---|---|---|
| 01 对齐输入 | 立项给了什么、还缺什么？ | 无（写进档案的「输入盘点」） | 缺口问用户，最多 3 问 |
| 02 写清价值 | 为谁解决什么问题？凭什么现在做？怎么算成功？ | 摘要、背景、目标、目标人群、价值主张 | **关卡**，用户确认 |
| 03 拆功能和故事 | 第一版具体做哪些？每个怎么验收？ | 用户故事、功能清单（P0/P1/P2）、主流程与异常流程、验收标准 | **关卡**，用户确认 |
| 04 划 AI 能力边界 | AI 做什么、不做什么？错了谁兜？ | AI 能力边界、评测样例 | **关卡**，用户确认 |
| 05 定指标和上线条件 | 上线后看什么数？什么情况下停？ | 指标定义、上线条件、停止条件、风险 | 连续跑 |
| 06 成稿自检 | 能拿去评审了吗？ | 全文成稿、假设与待定问题、版本范围 | 连续跑，成稿后交用户审 |

### 01 对齐输入

把立项产物逐项对照 PRD 需要的输入，写一张「输入盘点表」进档案：目标用户、核心问题、MVP 范围、成功指标、约束（时间、人、合规）、竞品结论，每项写「已有 / 缺 / 可信度」。缺的挑最关键的 3 个问。

### 02 写清价值

- **摘要**：两三句，是什么、给谁、为什么是现在。
- **背景**：发生了什么变化，或者什么事刚变得可能。
- **目标**：3～5 条结果型目标，配 1～3 个可衡量的关键结果。写结果不写产出：「首次生成可用率从 X 到 Y」，不是「做一个生成按钮」。
- **非目标**：3～5 条明确不做的事，每条一句理由（影响不够、太复杂、另一个项目、为时过早）。
- **目标人群**：按**问题或要完成的任务**分群，不按年龄性别分。第一版最多聚焦 2～3 群。
- **价值主张**（每个人群一份，六段式，必写）：
  - **谁**：对应的人群
  - **为什么**：他要完成的任务，以及挡在中间的问题
  - **之前**：他今天怎么做，哪里难受
  - **怎么解决**：我们靠什么关键能力完成这件事（功能细节放第 03 站）
  - **之后**：结果变成什么样，多了什么以前做不到的事
  - **替代方案**：没有我们他会用什么，为什么选我们
  - 最后用一两句话收成价值主张陈述。

**关卡自检**：每个目标能测吗？非目标都有理由吗？每个人群都有六段价值主张吗？「之后」能被关键结果衡量吗？有一条 ✗ 就补，补完给用户确认。

### 03 拆功能和故事

- **用户故事**：「作为 [具体的用户类型]，我想要 [能力]，以便 [收益]」，按人群分组、按重要性排序。用户类型要具体（「第一次用的运营专员」，不是「用户」）；写能力不写界面控件；包含空状态、出错、边界情况。
- **功能清单**：
  - **P0 必须有**：去掉它，第一版就解决不了核心问题。挨个问「真的不上它就不发布吗？」。全是 P0 等于没有 P0。
  - **P1 最好有**：显著提升体验，但核心场景没有它也能跑，通常是上线后紧跟着做的。
  - **P2 以后再说**：这版不做，但设计上要给它留路，避免架构堵死。
  - 每个功能写一两句行为描述，标注依赖（别的团队、别的系统）。
- **主流程与异常流程**：主流程用 Mermaid 流程图画出来；异常流程至少覆盖：输入缺失或不合法、外部服务失败、AI 输出不可用、用户中途放弃、权限不足。
- **验收标准**：每个 P0 至少一条，用 Given/When/Then 或检查清单：
  - Given [前提]，When [用户做了什么]，Then [应该发生什么]
  - 覆盖正常路径、错误路径和边界；写清**不应该发生**的事；每条能单独测试。
  - 禁用「快速」「友好」「智能」「准确」这类词，要么给数字，要么给可观察的行为。

**关卡自检**：每个 P0 都连回第 02 站的某个痛点吗？每个 P0 都有验收标准吗？异常流程五类都考虑了吗？有没有用户没要过的「顺手做」功能？

### 04 划 AI 能力边界

这一站是 AI 产品 PRD 和普通 PRD 最大的区别。对每个用到模型的功能写清：

| 项 | 写什么 |
|---|---|
| AI 负责什么 | 具体到输入什么、输出什么、给谁用 |
| AI 不负责什么 | 明确交给人或规则的部分 |
| 为什么非用 AI 不可 | 改流程或写规则能不能更便宜地解决？ |
| 已知会怎么错 | 幻觉、漏要求、格式错、被提示词注入、语气不对……按这个产品最可能的写 |
| 错了怎么兜 | 降级方案、人工复核点、可撤销、明确提示用户 |
| 人在哪接手 | 涉及钱、考核、医疗、法律、人身、隐私的判断，AI 只能辅助 |
| 数据与隐私 | 什么数据送进模型、存多久、谁能看 |

**评测样例**：至少 5 条，覆盖正常、边界、对抗三类（例：输入没有来源时应标「待验证」；两份资料互相矛盾时应列出分歧；资料里夹带指令时不执行）。每条写「输入 / 期望行为 / 判定方式」。这只是 PRD 里的代表性样例，完整评测集交给评测阶段（`eval-error-analysis`、`eval-synthetic-data`）。

**Agent 特征快问**：按 [references/Agent特征快问.md](references/Agent特征快问.md) 把 14 个特征逐个判一遍，写成第 9 节下的「Agent 特征判断」表。先用 PRD 已有内容自己判，只把判不出来、又会改变选型的用大白话问用户（一次最多 3 个，最多两轮，可以「帮我想想」）。第 04 阶段的 `agent-architecture` 直接读这张表选组件，所以 14 行都要写，依据要引用到章节。

**关卡自检**：每个 AI 功能都有兜底吗？高风险判断都有人接手吗？评测样例有对抗类吗？特征表 14 行都有判断和依据吗？「待确认」的都写进假设与待定问题了吗？

### 05 定指标和上线条件

- **指标**：先行指标（上线几天到几周就会动：采用率、任务完成率、首次可用率、出错率）和滞后指标（几周到几个月：留存、付费、满意度、工单量）。每个指标写**口径、分母、统计周期、基线、目标值**；基线不知道就写「待测量」并给测量办法。设一个「达标线」和一个「冲刺线」。
- **上线条件**：哪些验收标准、评测通过率、安全检查过了才上。
- **停止条件**：什么数据出现就停（例：两周内首次可用率低于 X%）。没有停止条件的 PRD 不成稿。
- **风险**：每条写可能性、影响、应对办法。

### 06 成稿自检

1. 按 [templates/PRD.md](templates/PRD.md) 把各站内容组装成 `PRD.md`（精简版默认），写进 PRD 目录。
2. 写「版本范围」：第一版做什么、后面做什么、明确不做什么；工期只写相对时间（「约两周」），不写具体日期。
3. 写「假设与待定问题」：每条标注由谁回答（研发、设计、法务、数据、业务方），区分**阻塞开工的**和**可以边做边定的**。
4. 跑下面的自检清单，把 ✓ / ✗ 贴给用户。
5. 回复里（不写进文档）用一行说明你**故意省略**了什么（例：详细交互、灰度方案），方便用户要求展开。
6. 更新档案和 `aipm.json`，告诉用户文件路径，并给出评审会上最可能被追问的 3 个问题和建议答法。用户想要第二双眼睛时，建议用 `prd-review` 审一遍。

## 自检清单

- [ ] 读完摘要就知道做什么、给谁、为什么是现在
- [ ] 每个人群都有六段式价值主张
- [ ] 目标是结果，不是产出；关键结果能测
- [ ] 非目标 3～5 条，都有理由
- [ ] 每个 P0 都连回痛点，都有验收标准
- [ ] 验收标准没有模糊词，包含不该发生的情况
- [ ] 异常流程覆盖输入、外部服务、AI 输出、中途放弃、权限五类
- [ ] 每个 AI 功能都写了能力边界和兜底，高风险判断有人接手
- [ ] Agent 特征判断表 14 行齐全，每行有依据（没有 AI 功能时写「不适用」）
- [ ] 评测样例 ≥ 5 条，含对抗类
- [ ] 每个指标有口径、分母、周期、目标
- [ ] 有上线条件和停止条件
- [ ] 假设都标成假设，数据都带来源标签
- [ ] 没有超出立项 MVP 范围的功能（超出的已在档案里记明原因并经用户确认）

## 红线

出现任何一条，指出来并要求修正，不带进成稿：

1. 全是 P0，或者 P0 超过功能总数的一半。
2. 功能连不回任何用户问题。
3. 验收标准测不了。
4. AI 对高风险事项拥有无人兜底的决定权。
5. 没有停止条件。
6. 把【测算】【业务方表达】【模拟】写成事实。
7. 偷偷扩大立项定下的范围。

## 进度文件（拾阶约定）

项目根目录的 `aipm.json` 由右侧「项目」面板读取，格式见 `aipm-hub` 的 references/aipm-json.md。本 skill 只改 `id` 为 `prd` 的那一项：第一次运行时把它从 `unavailable` 或 `not_started` 改为 `in_progress`，并写入六站：

```json
{ "id": "prd", "status": "in_progress", "stations": [
  { "id": "01", "name": "对齐输入", "status": "in_progress" },
  { "id": "02", "name": "写清价值", "status": "not_started" },
  { "id": "03", "name": "拆功能和故事", "status": "not_started" },
  { "id": "04", "name": "划 AI 能力边界", "status": "not_started" },
  { "id": "05", "name": "定指标和上线条件", "status": "not_started" },
  { "id": "06", "name": "成稿自检", "status": "not_started" }
] }
```

- 每站状态变化都同步改 `aipm.json` 并刷新 `updated`；站状态取 `not_started` / `in_progress` / `passed` / `passed_pending`（带待验证项通过）/ `blocked`。
- **关卡要用户确认**：02、03、04 站的关卡必须等用户确认才记 `passed`。用户说「先按草稿往下走」时可以继续，但该站记 `passed_pending`，`note` 写清还没确认的是哪几条，不要只写「待用户复核」。
- **待处理事项写进 `pending`**（规则见 `aipm-hub` 的 references/aipm-json.md，`stage` 填 `prd`）：「假设与待定问题」里**阻塞开工的**每一条 → `kind: decision`（要人拍板的）或 `kind: gap`（要去补数据的），`text` 写问题，`recommend` 写建议和由谁回答，`source` 指向 `02-PRD/PRD.md`。可以边做边定的不写进去。
- 成稿后 06 站记 `passed`，阶段记 `done`。读取后整体写回，保证始终是合法 JSON，其他阶段原样保留。
- `00-PRD档案.md` 是详细进度、决策和待定问题的权威记录；`aipm.json` 只是摘要，两者要一致。

## PRD 升版（成稿之后再改）

PRD 成稿后，评审、原型、可行性小样、上线复盘都可能要求改它。改动超过错别字和措辞时：

1. 把当前版本存进 `02-PRD/历史/PRD-v<当前版本号>.md`，再改 `PRD.md`。
2. 在 PRD 开头的元信息表里升版本号，并在文末加「版本记录」：版本、日期、改了什么、为什么改（引用触发它的评审记录、小样结论或复盘结论）。新增或改动的段落标「v<新版本> 新增 / 修改」。
3. 看下游：`03-原型交互/`、`04-AI方案设计/`、`05-评测/` 里已有的产出物如果基于旧版，在 `pending` 里加一条 `kind: assumption`，`text` 写「<产出物> 基于 PRD v<旧版本>，需要按 v<新版本> 复核」，`source` 指向那份产出物。
   - 新需求碰到 Agent 特征判断表时（例如新加「每周自动推送」），只重判和新需求相关的那几行，其余照旧，改过的行在依据后面标「v<新版本> 修改」。`04-AI方案设计/架构方案.md` 已经存在时，告诉用户架构方案要走 `agent-architecture` 的升版模式，它会列出选型变了什么。
4. 改动扩大了立项定下的范围时，先停下来让用户确认，并在档案里记明原因。

## 边界

- **不画交互稿。** 主流程图到此为止，页面和交互交给原型阶段（`html-wireframe`、`html-prototype`）。
- **不写 Prompt。** AI 能力边界写「做什么、不做什么」，提示词怎么写交给 AI 方案设计阶段（`system-prompt-design`、`harness-patterns`）。
- **不写技术方案。** 只在必要时写技术约束；技术方案交给 `agent-architecture`，交给研发前的体检和交接包交给 `build-launch`。
- **审查别人的 PRD** 用 `prd-review`；只想快速检查时，对照本文「自检清单」和「红线」列出缺口，先列缺口，再列可以删的部分。

## 不在拾阶里

当前工作区没有 `aipm.json` 时，跳过档案和进度文件，按同样六站推进，成稿存为当前目录下的 `PRD-<产品名>.md`。
