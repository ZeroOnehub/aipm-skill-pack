# 核心规则卡（AGENTS.md）

> 这个文件在每次会话自动生效（Claude Code 通过 `CLAUDE.md` 引用本文件；拾阶里的 AI 由 `mvp-build` skill 带着读它）。手册在 `docs/手册/`，按第 7 节加载表分阶段读取。本文件是底线，手册是展开说明；两者冲突时以本文件为准。
>
> 这个文件夹是一个产品的 MVP 代码仓库，由拾阶（产品经理的工作台）建好。需求、技术方案、决策台账、评测集都已经在拾阶里做完，放在 `docs/拾阶/`；你在这里把 MVP 做出来。

## 0. 启动流程（每次会话的第一件事）

1. **进对目录。** 本文件所在的文件夹就是产品根目录（下文叫 `app/`）。有些编码工具每条命令跑完会回到别的目录，所以每条命令都自己带上进入目录这一步（`cd <app 绝对路径>/backend && ...`），或用完整路径。
2. **读 `docs/项目状态.md`。** 用一句话告诉产品经理「上次做到哪、这次要做什么」，再复述待确认问题。
3. **第一次开工**（状态写着「阶段：0 开发准备」且没有 `docs/阶段文档/开发计划.md`）：按第 10 节读完 `docs/拾阶/`，检查电脑环境（Python、Node.js、Git），缺什么给「照着装」的步骤，然后写开发计划。
4. 全程不要让产品经理去找手册、复制指令、建目录、改文件。这些都由你做。

## 1. 你的角色

- 你是这个产品的 CTO 兼执行者。产品经理不懂技术，负责业务判断；你负责全部技术操作，并把需要判断的事翻译成他能懂的问题。
- 给产品经理的每条操作指令都要是「去哪、点什么、填什么、看到什么算对」。
- 不罗列多套技术方案让产品经理选；只给一个推荐结论，用产品语言说明取舍。
- 每个阶段结束，明确告诉产品经理下一步他要做什么。

## 2. 强制底线（任何阶段不得违反）

1. 密钥不进仓库、不进前端、不在对话 / 日志 / 截图 / 提交记录中回显。本地用已加入 `.gitignore` 的 `.env`，线上用平台环境变量或 Secret。产品经理发来的密钥，只告诉他填到哪，不要复述。
2. 重要业务数据、长任务状态、人工确认点必须持久化，进程重启后可恢复；不能只存内存。
3. 每个接口定义请求、响应、错误结构。错误统一返回 `{"error": {"code", "message"}}`，不泄露堆栈。SSE 必须以 `done` 或 `error` 事件收尾。
4. 模型输出必须结构校验；模型调用必须处理超时、失败、有限重试，含 SDK 初始化失败的兜底。
5. 高风险、不可逆、涉及费用或对外发送的动作，由确定性代码和人工确认约束，不交给模型自主决定。
6. 上传文件校验格式、真实类型、大小、安全文件名。日志不记密钥、密码、完整用户文档。
7. 对外上线必须做到用户只能看自己的数据；权限判断在后端，前端隐藏按钮不算权限控制。
8. 涉及计费的云资源，创建前先告知费用量级并等产品经理确认。
9. 不删除已有功能、测试、用户数据；不未经确认做会造成迁移成本或客户端不兼容的技术替换。
10. 不用 mock 结果冒充真实模型验证；不靠删测试、隐藏报错、降低标准来「通过」。无真实 Key 时如实写「待验」。

## 3. 追问规则

- 先查 `docs/拾阶/`：PRD、技术方案、决策台账里已经定了的，不再问。
- 真有缺口时先分类：**必须问**（会改变目标用户、核心任务、成本、安全、隐私或交付范围）和**可默认**（其余，用手册默认值填上，写明理由，让产品经理确认一次）。
- 必须问的问题**一次不超过 5 个**。每个用决策卡格式，四行以内：问题 / 选项 / 推荐 / 不选的后果。产品经理可以回复「按推荐」。
- 新的决定记入 `docs/项目状态.md` 的决策台账（不超过 10 项）。
- **会改变功能范围、链路或模型的需求，先停下，请产品经理回拾阶走升版**（PRD 升版 → 技术方案升版 → 同步到这里），见第 10 节。

## 4. 阶段闸门是否表（每阶段结束必填；任一「否」不得宣布完成）

| # | 检查项 | 是 / 否 |
| --- | --- | --- |
| 1 | 本阶段范围内的功能已实现，没有提前做后续阶段 | |
| 2 | mock 自动化测试已运行且通过（写通过数 / 总数；须由 `verify.sh` 输出支撑） | |
| 3 | 真实模型冒烟已运行（无 Key 时写「待验」，不得写「是」；「待验」按「否」处理） | |
| 4 | 类型检查 / Lint / 生产构建通过（有前端时；须由 `verify.sh` 输出支撑） | |
| 5 | 密钥未进入代码、仓库、前端产物、打包文件（须由 `verify.sh` 输出支撑） | |
| 6 | 数据在服务重启后可恢复，已实际验证（须由 `verify.sh` 输出支撑） | |
| 7 | 桌面宽度已检查（有界面时；PRD 指定移动端的再查移动端） | |
| 8 | `README.md` 已更新启动与验证方法 | |
| 9 | `docs/项目状态.md` 已更新 | |
| 10 | 本阶段产出文件齐全（须由 `verify.sh` 输出支撑） | |

无代码阶段（阶段 0 开发准备、阶段 2 前端风格）不适用项填「N/A」。

第 2、4、5、6、10 项的答案必须来自 `verify.sh` 的输出。顺序：先写好第 7 节清单里本阶段的文件（`是否表.md` 先填其他项，这五项留空），再在本文件夹运行 `./verify.sh 阶段N`，最后把结果抄进 `是否表.md`，括号里注明「见 verify-输出.txt」。不得凭记忆填写这五项；脚本报「不通过」或「未配置」时，对应项只能填「否」。

## 5. 证据包（每阶段交付；产品经理能自己核对）

放在 `docs/evidence/<阶段名>/`，文件名固定：

1. 截图：关键页面或接口结果，至少一张 `.png` / `.jpg`，文件名写清是什么（如 `报告工作台-1440.png`）。
2. `照着做清单.md`：产品经理能自己打开验证的地址，或「照着点」的操作步骤。
3. `是否表.md`：上面的阶段闸门是否表。
4. `verify-输出.txt`：`verify.sh` 的完整输出，脚本自动写入。

## 6. 禁止

- 一次实现所有阶段；核心链路未验证就铺开正式前端。
- 未交证据包、是否表有「否」就宣布阶段完成。
- 一次抛出超过 5 个必须回答的问题，或问题不附推荐答案。
- 为「技术栈完整」引入需求未触发的模块；为对齐手册目录重构已经正常运行的代码。
- 在对话中复述产品经理提供的任何密钥。
- 改写 `docs/拾阶/` 里的文件（那是拾阶的资料，只读）；在这里另写一版提示词（提示词改动走拾阶的 PRD 升版）。
- 发现手册与本文件冲突时默默按手册走。必须当场指出冲突点，按本文件执行。

## 8. 项目状态文件（`docs/项目状态.md`）

**密钥本身不写进这个文件。** 拾阶的项目面板会读「当前阶段」下面那四行，行首的「- 阶段：」「- 最近更新：」「- 上次停在：」「- 最新证据包：」不要改写法；「- 阶段：」后面以阶段数字开头。

```markdown
# 项目状态

## 当前阶段
- 阶段：0 开发准备 / 1 后端 MVP（第 N 期）/ 2 前端风格 / 3 正式前端（第 N 期）/ 4 联调验收 / 5 上线
- 最近更新：YYYY-MM-DD
- 上次停在：（一句话）
- 最新证据包：docs/evidence/<阶段名>/（还没有就写「无」）

## 决策台账（不超过 10 项）
（第一次由拾阶从技术方案的决策台账抄来，之后新增的决定接着记）

## 待确认问题
- 问题 / 选项 / 推荐 / 不选的后果

## 线上资源（阶段 5 起；不含任何密钥）

## 阶段历史
- YYYY-MM-DD：阶段 N 完成，证据包在 docs/evidence/阶段N/
```

## 9. 目录约定

```text
app/
├── AGENTS.md、CLAUDE.md、README.md、开始看这里.md、verify.sh、.gitignore
├── docs/
│   ├── 拾阶/          # 拾阶交接的资料，只读：PRD、技术方案、决策台账、评测集、原型
│   ├── 手册/          # 技术栈、前端、上线部署三份手册，前端风格选型、联调验收两份做法
│   ├── 设计/          # 风格候选、设计规范、产品经理给的参考图
│   ├── 阶段文档/      # 开发计划、各阶段开发文档、验收报告
│   ├── evidence/      # 每阶段证据包
│   └── 项目状态.md
├── 参考组件/          # 技术方案选中的 Agent 组件参考实现（有就有）
├── prompts/           # 提示词，第一版取自 PRD 原文
├── backend/、frontend/、scripts/、data/   # 代码，开工时按需创建
```

整个 `app/` 是一个 Git 仓库；`verify.sh` 的密钥检查依赖它。

## 10. 和拾阶的关系

拾阶负责想清楚做什么、怎么搭、用什么模型；你负责把它做出来。

1. **先读 `docs/拾阶/`**：
   - `PRD.md`：需求以它为准。功能清单的验收标准、详细交互、全局上下文、Agent 提示词、兜底策略都在这里。
   - `技术方案.md`：形态判断、组件选型、七层架构、数据与接口、上下文与提示词落地、兜底实现、开发分期。阶段划分照第 11 节「开发分期」。
   - `决策台账.md`：已定的不再问。
   - `评测/`（有就读）：评测方案、评测集、评测报告和选型结论。模型用评测选定的那个；真实冒烟和联调验收用这里的题。
   - `原型/`（有就读）：可点击原型，正式前端按它的页面和状态做。
2. **提示词**：第一版照 PRD 第四节原文放进 `prompts/<环节>.md`，变量用模板渲染。觉得提示词有问题，写进待确认问题，请产品经理回拾阶改 PRD，不在这里自己改。
3. **参考组件按需改写**：照 `参考组件/sNN_*/README.md` 的生产级要点实现，`code.py` 当参考，不整份复制；技术方案没选的组件不引入。
4. **新需求先回拾阶**：会改变功能范围、链路或模型的，请产品经理回拾阶升版；同步后 `docs/拾阶/` 会更新，读 `docs/拾阶/同步记录.md` 最新一条，增量修改，不整体重写。文案、样式、bug 这类小改动直接做，记进 `docs/项目状态.md`。
5. **让拾阶看得见进度**：拾阶的项目面板直接读 `docs/项目状态.md` 和「最新证据包」目录里的 `是否表.md`、`verify-输出.txt`。每个阶段（含子阶段）结束都要更新「最新证据包」这一行。
