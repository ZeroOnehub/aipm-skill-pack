# MVP

## 一句总纲

**MVP 是用来验证的，不是用来展示的：核心链路先用真实模型跑通，再做界面；每个阶段交证据，不交口头汇报。**

## 两层规则

- **这个 skill**：拾阶这边的事——建仓库、同步资料、带产品经理做决定（挑风格、验收）、把进度写回 `aipm.json`。
- **代码仓库里的 `AGENTS.md`**：写代码的规则——十条底线、是否表、证据包、阶段与手册加载表。**不管是你（拾阶里的 AI）还是 Claude Code、Codex 来写代码，都照它做。** 安装以后先读一遍它，后面每个阶段开工前读它第 7 节对应的手册部分。

## 开场

1. 定位项目；MVP 目录是 `<项目根目录>/06-MVP/`，代码仓库默认在 `06-MVP/app/`（`aipm.json` 的 `build.path` 记着实际位置）。
2. 检查前置：`02-PRD/PRD.md`、`04-技术方案/技术方案.md` 必须有；`05-模型评测/评测报告.md` 没有的，告诉用户模型还没评测、真实冒烟没有题可用，建议先做 05；用户坚持先做，记一条 `assumption`「模型未经评测」。
3. 已经装过（`build.path` 存在）：读 `<build.path>/docs/项目状态.md`，告诉用户做到哪个阶段、最新是否表有没有「否」，从那里继续。

## 五站

| 站 | 代码仓库里的阶段 | 谁做什么 | 产物（在 `app/` 里） | 关卡 |
|---|---|---|---|---|
| 01 开发准备 | 阶段0 | 你：运行安装脚本，读 `docs/拾阶/`，查环境，写开发计划；产品经理：确认计划、申请模型 Key 并**自己**填进 `backend/.env` | `docs/阶段文档/开发计划.md`、证据包 | 计划经确认；verify.sh 阶段0 通过 |
| 02 后端 MVP | 阶段1-1、1-2…… | 你：按技术方案分期写后端，用评测集的题做真实冒烟；产品经理：照着做清单验收、对 5–10 条真实样例打分 | 每期开发文档、代码、证据包 | 每期是否表全「是」 |
| 03 前端风格 | 阶段2 | 你：上网找参考，把代表页做成 3–4 种风格；产品经理：挑一个、提修改 | `docs/设计/风格候选.html`、`docs/设计/设计规范.md` | 产品经理选定 |
| 04 正式前端 | 阶段3-1、3-2…… | 你：按原型和设计规范写前端；产品经理：看代表页、亲手走一遍 | 每期开发文档、代码、证据包 | 每期是否表全「是」 |
| 05 联调验收 | 阶段4 | 你：评测集走真实链路、功能逐条对照、兜底抽查；产品经理：照着做清单走一遍，确认结论 | `docs/阶段文档/验收报告.md`、证据包 | 红线 0；结论经产品经理确认 |

做完 05 想上线的，照代码仓库 `AGENTS.md` 第 7 节的阶段 5 和上线部署手册走，不算在这五站里。

### 01 开发准备

```bash
python3 <本 skill 目录>/scripts/install_app.py --project <项目根目录> --tool 拾阶
```

脚本做的事见它的开头说明；它会在 `aipm.json` 写好 `build`。用户想用 Claude Code、Codex 写代码时 `--tool` 写对应名字，并把代码仓库里 `开始看这里.md` 的「谁来写代码」一节转述给他。

然后照 `app/AGENTS.md` 第 0 节启动：读完 `docs/拾阶/`，查环境（Python 3.12、Node.js、Git），照 `docs/阶段文档/开发计划-模板.md` 写开发计划（分期取自技术方案第 11 节，每期配几道评测题做冒烟），给用户看。告诉用户去哪申请评测选定的那家模型的 Key、填到 `backend/.env` 的哪一行；**不要让用户把 Key 发在对话里，发了也不要复述**。

### 02 后端 MVP

照 `app/AGENTS.md` 和通用技术栈手册第二、三部分。要点：

- 提示词用 `prompts/` 里从 PRD 抽出的原文，不自己改。觉得要改，写进待确认问题，请用户回 PRD 升版后 `--sync`。
- 模型用评测报告选定的那个，备用模型也接上。
- 每期结束用开发计划里指定的评测题做真实冒烟（`docs/拾阶/评测/run_eval.py` 的 `--app-url` 模式，做法见 `docs/手册/联调验收.md` 第 1 节；评测入口在阶段 1 就可以先加上）。
- 没有 Key 时 mock 测试照样推进，但是否表第 3 项只能写「待验」，阶段不算完成。

### 03 前端风格

照 `app/docs/手册/前端风格选型.md`。你负责上网找参考、做 `风格候选.html`；用提问工具请用户选（每个选项写方向名和一句适合的理由，推荐的放第一个）；选定后写 `设计规范.md`。

### 04 正式前端

照前端技术栈手册、`docs/设计/设计规范.md` 和 `docs/拾阶/原型/`。页面编号沿用原型的 P01、P02；状态（空、加载、流式、失败、兜底）照原型和 PRD 第七节做全。

### 05 联调验收

照 `app/docs/手册/联调验收.md`。验收报告的结论用提问工具请用户确认（通过 / 有条件通过 / 不通过）。

## 同步

PRD、技术方案或评测升版以后：

```bash
python3 <本 skill 目录>/scripts/install_app.py --project <项目根目录> --sync
```

只刷新 `docs/拾阶/`，旧版存进 `docs/拾阶/历史/`，在 `docs/拾阶/同步记录.md` 记一条。然后读同步记录最新一条和技术方案的变更记录，**增量修改**代码，不整体重写。

## 进度写回

每站结束（也就是代码仓库里每个阶段结束）：

1. 读 `app/docs/项目状态.md` 的「- 阶段：」一行，原样写进 `aipm.json` 的 `build.stage`，`build.checked` 写今天。
2. `aipm.json` 里 `id` 为 `mvp` 的阶段：第一次运行写入五站（`01 开发准备`…`05 联调验收`）并改为 `in_progress`；代码仓库阶段 0 完成 → 01 `passed`；阶段 1 全部子阶段完成 → 02 `passed`；依此类推。是否表有「待验」的记 `passed_pending` 并在 `note` 写待验什么；verify.sh 不通过或是否表有「否」记 `blocked`。
3. 05 通过后阶段记 `done`。告诉用户：怎么启动产品（`app/README.md`）、验收结论、已知问题；想上线的下一步是代码仓库的阶段 5。

只改 `id` 为 `mvp` 的阶段、`build`、和 `stage` 为 `mvp` 的 `pending`；改之前先读、整体写回，刷新 `updated`。

## 风格

- 给用户的每条操作指令都写成「去哪、点什么、填什么、看到什么算对」，一次只给当前这一步。
- 汇报进度引用证据包：「阶段1-1 的是否表 10 项 9 个是、1 个待验（真实冒烟缺 Key），见 docs/evidence/阶段1-1/」。
