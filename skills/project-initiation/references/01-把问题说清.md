# 第 01 站 · 把问题说清

**要回答：** 到底是个什么问题？该不该用 AI？
**交付：** `01-问题定义卡.md`（模板：[templates/01-问题定义卡.md](../templates/01-问题定义卡.md)）

## 三步 + AI 多问一句

### 1. 还原场景

问完这五样，才轮到谈功能：

| 要素 | 追问到什么程度 |
|---|---|
| 谁 | 具体到一类人，有身份、阶段、处境，不是「年轻人」「白领」 |
| 何时何地 | 几点、在哪、跟谁、在什么节点上（如月底、上线前、入职第一周） |
| 在做什么 | 手上正忙什么任务 |
| 卡在哪 | 哪一步过不去 |
| 现在怎么凑合 | 没有你，他怎么办？花了多少时间、钱、人力？ |

「现在怎么凑合」最重要：它就是你的替代品竞品，也是用户痛不痛的证据。用户没在凑合（什么都不做也无所谓），这个问题多半不疼。

### 2. 分开问题和方案

- 听到功能名（「做个小程序」「上个 AI」「做个助手」），反问一句：**有了它，你想解决什么？**
- 改写成「谁 · 什么场景 · 卡在哪」的句子。
- 改完检查：**句子里找不到一个功能名或技术名。**

业务方、老板给的往往是方案。方案不是错的，但它只是解决问题的一种可能。先把问题写出来，方案留到第 05 站再比较。

### 3. 问三次为什么

- 每次只追一层。
- 对照他做过的事：手上做的比嘴上说的可信。说「太麻烦不想做」，但每月都在用笨办法做，说明需求是真的，只是现有方式太贵。
- 停在能动手的一层。再往下追就超出产品能改变的范围（比如「因为人性懒」），停在上一层。

### ＋ AI 多问一句：该不该用 AI

三个条件**同时满足**才考虑用 AI：

| 条件 | 判断方法 |
|---|---|
| 重复性高 | 每个人、每次都在做同样的事 |
| 标准化程度高 | 好坏说得清，有可执行的评判标准 |
| 人力瓶颈明显 | 人不够、太贵、要排队 |

再追问两句：

1. **改流程能不能更便宜？** 改个排班、加个模板、调个规则就能解决的，不用 AI。
2. **模型变强以后，我们更值钱还是被吞掉？** 如果通用大模型下个版本就能直接做到，我们的壁垒在哪（数据、场景、流程、渠道）？

注意「标准化程度高」最容易被高估：业务方说「有明确的三级标准」，要去看真实的评分记录。同一个结果不同人打分不一样、标准写的和实际用的不一样，说明人自己都没统一，AI 不知道该学谁。这种情况要写进问题定义卡的「AI 适配判断」，作为第 06 站的前置风险。

## 1→N 项目的额外步骤

先写一句话业务公式，把核心指标拆成可干预的因子，再拿漏斗或旅程数据找流失最大的段落。每个主要流失段写一张问题定义卡，卡片数量控制在 2 到 4 张。见 [立项类型差异.md](立项类型差异.md)。

## 怎么问用户

开场先请用户用一句话说想做什么。然后：

1. 如果是方案，先复述，确认没听错，再问「有了它想解决什么」。
2. 按五要素追问，每次挑最模糊的 2 到 3 样问，先给你的猜测。
3. 问三次为什么时，每轮给用户两三个可能的「为什么」让他选或改。
4. 最后你起草问题定义卡，请用户改。

## 自检清单（关卡）

- [ ] 「谁」具体到一类人，能想象出一个真人
- [ ] 场景写了时间、地点或节点
- [ ] 「现在怎么凑合」写的是具体行为，并有代价（时间 / 钱 / 人 / 后果）
- [ ] 一句话问题定义里**没有任何功能名或技术名**
- [ ] 追到了能动手的一层，没有停在表面抱怨，也没有追到改不了的地方
- [ ] AI 三条件逐条判断，并回答了「改流程能不能更便宜」
- [ ] 每条事实带证据标签；只有【业务方表达】或【AI 推断】的，标为待验证，并写进第 02 站要验证的事项
