# 第 06 站 · 拍板立项

**要回答：** 值不值得投人、投钱？
**交付：** `立项报告.md` + `立项报告.html`

## 先对齐决策对象

读档案里的「决策对象」：这次批的是哪一步（想法 → POC、POC → MVP、MVP → 试点、试点 → 全量）、多大范围。下面的所有判断都只针对这一步。批 POC 时，「开发难不难」问的是 POC 做不做得出来，不是全量上线难不难。

## 四步

### 0. 事前验尸

打分之前，先按 [事前验尸.md](事前验尸.md) 假设项目一年后失败了，倒推原因，分出老虎、纸老虎、大象。「立项前必须解决」的老虎直接进入「需要您拍板的事」或第一个闸门；大象登记进假设地图。

### 1. 过三问

| 问题 | 等于问 | 证据来自 |
|---|---|---|
| 用户买不买？ | 市场有蛋糕吗？ | 第 02 站 |
| 公司赚不赚？ | 能赚到钱、或换到公司要的东西（知名度、留存、战略位置）吗？ | 第 01、04 站 |
| 开发难不难？ | 我们能做吗？买现成的会不会更划算？ | 第 05 站、AI 四问、第 04 站的替代品 |

### 2. 决策矩阵打分

每问 1 到 5 分，**每个分数写一句理由和证据标签**。

| 分数 | 含义 |
|---|---|
| 5 | 证据充分，明显有利 |
| 4 | 有证据，偏有利 |
| 3 | 证据不足或利弊相当 |
| 2 | 有证据，偏不利 |
| 1 | 证据充分，明显不利 |

**先查一票否决**：隐私、合规、数据权限、安全、资金红线，任何一条没过，不论三问打多少分，结论都不能是「做」。一票否决项单独列出来，不参与打分。

结论四选一：

- **做**：三问都在 4 分以上，AI 四问都答得上来，没有一票否决项。结论只批到决策对象那一步，写清批准范围、前提和下一次评审的闸门。
- **有条件做（先验证）**：机会有基础，但还有能改变决定的假设没验。写清条件、试点范围、闸门，每个闸门一张实验卡（见 [假设地图与验证实验.md](假设地图与验证实验.md)）：要验证的假设、方法、样本或流量范围、指标、门槛、负责人、时长、成本上限、停止条件。
- **搁置**：现在不值得投入，但不是想法错了（时机不对、资源被更重要的事占着、前置条件没就位）。写清**什么条件出现时重新评估**。
- **不做**：有足够的反面证据、致命约束、买现成的明显更好，或风险不可接受；或 AI 适配三条件不满足且改流程更便宜。

**缺证据时不出结论**：如果连决策对象都说不清，或者关键证据缺得太多、连「先验证什么」都定不下来，就写「暂不出结论，先补证据」，给出最多 3 个能改变决定的问题和一份最小的补证据计划。缺证据本身不能当成「不做」的理由。

分数是辅助，不是公式。最终结论要用一段话讲清楚取舍：选了什么、为什么、代价是什么。结论是「不做」「搁置」「有条件做」或「暂不出结论」时，停下来跟用户确认。

**「不做」也是合格的立项结论。** 报告照样写完整，重点写清为什么不做、什么条件变了值得重新评估。

### 3. AI 多问四句

读 [AI四问.md](AI四问.md)，逐问回答，写进报告第 07 节。任何一问答不上来，就停下来问用户；问完仍然答不上来的，结论最多是「有条件做」，并把这一问变成第一个闸门。

## 分阶段批钱

AI 项目的不确定性大，钱最好分阶段批，**先批到评测为止**。

- 每个阶段写：先验证什么、主要产出、通过标准、**不过闸怎么办**（停止 / 降级 / 转向）。每个闸门背后是一张实验卡，判定标准在开始之前写死。
- 常见顺序：统一标准与评测集 → 离线或异步验证 → 在线或实时能力 → 小范围试点 → Go / Continue / Pivot / Stop 决策。
- 高风险判断场景用**影子模式**：AI 跟着跑，不做决定，拿它的输出和人的判断对比。

## 停止条件

每份报告都必须有。写成可观测的条件：

- 某个评测指标在某个时间点前达不到门槛。
- 试点期用户使用率低于某个值。
- 出现某类安全或合规事件。
- 关键前置（数据权限、合规审批、标准统一）在某时间点前未就位。

## 收益与数字的写法

- 历史材料里的收益测算、效率提升，照写但**标【测算】，写来源和口径，注明未经上线验证 / 未经财务复核**。
- 分组对比数据（用了的组 vs 没用的组）只能说明相关；写清样本量、分组方式、未控制的变量。
- 首期验收指标优先选**能在试点期内直接观测**的（使用率、完成率、人工工时、评分一致性、准确率），不要把收入、业绩这类受太多因素影响的指标设成首期硬验收。
- 没有历史数据支撑的预测（如「转化率提升 X 个百分点」），不给具体数字，写「先建基线，某时间点后定目标」。

## 1→N 项目：版本节奏

1. 找一个**外部锚点**（大促、新品上市、财年节点、合规截止日），倒推版本窗口。
2. 把专题和需求排进版本，每一版写重点和理由。
3. 按团队看每一版谁出力，标出最紧的一版和原因。
4. 写明「当前分配只是需求范围，尚未经研发估算」，容量对齐放进决策待办。
