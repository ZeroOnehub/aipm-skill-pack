# 第 05 站 · 排出先后

**要回答：** 先做哪个？第一版做多小？
**交付：** `05-MVP范围表.md`（模板：[templates/05-MVP范围表.md](../templates/05-MVP范围表.md)）

## 三步

### 0. 先问一句

对需求池里每一条先问：**这一版不做它，要验证的假设还成不成立？** 不影响的，直接往后放。

### 1. Kano 分类

| 类型 | 特征 | 处理 |
|---|---|---|
| 基本型 | 没有就不满意，有了也不加分 | 必须做 |
| 期望型 | 做得越好越满意 | 做差异 |
| 兴奋型 | 没有不会不满，有了很惊喜 | 放一个 |
| 反向型 | 做了反而让人烦 | 坚决不做 |

AI 产品里，**准确、可控、出错可纠正**通常是基本型；「AI 主动打扰用户」常常是反向型。

### 2. 四象限：价值 × 成本

| | 成本低 | 成本高 |
|---|---|---|
| **价值高** | 先做 | 排进规划 |
| **价值低** | 顺手做 | 不做 |

价值从第 02 站的证据来（多少人、多疼）；成本要算上 AI 特有的部分：数据准备、评测、模型调用费、合规审批、对接外部系统。拿不准成本时，标「待研发估算」，不要拍脑袋。

### 3. 定第一版：MVP

**每一版都要能用**：滑板 → 滑板车 → 自行车 → 汽车，不是先造轮子、再造底盘。

1. **先画假设地图，再写假设**：按 [假设地图与验证实验.md](假设地图与验证实验.md) 列出八类风险加 AI 三类的假设，按「错了会不会让项目失败 × 现在证据强不强」排序。**最危险的那条就是核心假设**，第一版只验证它（最多再加两三个辅助假设）。格式：「[某类用户] 在 [某场景] 下，会 [某行为]，达到 [某程度]」。
2. **只留必需的**：只保留验证这个假设必需的功能，每一条连回一个痛点。
3. **定通过标准**：什么结果算验证通过，要可测（如「N 天后，X% 的人仍在每周使用」）。成功、失败、说不清三种情况的判定标准，要在看到结果之前写死。
4. **先想最便宜的验法**：做 MVP 之前，问一句能不能用更便宜的实验先验核心假设（看现有凑合办法、假门测试、预售、礼宾式 MVP、绿野仙踪测试、离线 POC）。AI 产品尤其适合先做绿野仙踪测试：前台像 AI，后台由人完成，先验证用户要不要这个结果。

AI 项目通常要先分清三样东西：

| | 验证什么 | 给谁看 |
|---|---|---|
| POC | 技术做不做得到（拿真实数据测准确率是否过门槛） | 内部 |
| 原型 | 用户看不看得懂、想不想要 | 少量用户 |
| MVP | 用户会不会一直用 | 真实用户 |

AI 能力不确定时，第一版之前先跑 POC；能先异步、离线验证的，就别一上来做实时。

## 范围表三栏

- **必须做**：每条写连回的痛点。
- **明确不做**：每条写理由（成本高、反向型、依赖未就位、合规未批、AI 不该有这个权限、不是这一版要验证的）。
- **以后再说**：每条写什么条件下再做。

## 1→N 项目的额外步骤

1. **写取舍原则**：3 到 5 条，每条带「怎么判断」，后面所有需求按这几条排。
2. **按资源瓶颈排**：找出最紧张的团队。主要工作量不在瓶颈团队上的需求，单独列成「优先启动池」，可以立即排期；压在瓶颈团队上的列为「受限池」，按价值排，同时提人力申请，不因缺人而删需求。
3. **写砍需求顺序**（资源低于预期时）：

   | 层级 | 放什么 |
   |---|---|
   | L0 绝不砍 | 砍了就等于放弃本期目标的 |
   | L1 优先保 | 不占瓶颈的、用户反馈最集中的 |
   | L2 可后移 | 体验会打折但不影响主流程的 |
   | L3 先砍 | 短期不影响核心指标的深度能力、需等外部审批的 |

   原则：先砍占瓶颈资源的非关键项，最后才砍不占瓶颈的项（砍后者并不能缓解瓶颈，只会让有余力的团队闲着）。
