# 第 03 站 · 收进需求池

**要回答：** 到底有多少事要做？
**交付：** `03-需求池.md`（模板：[templates/03-需求池.md](../templates/03-需求池.md)）

## 三步

### 1. 拆动作

从调研结论推出动作，链条是：**用户 → 需求 → 场景 → 问题 → 动作**。

- 一个问题可以推出多个动作，先都写下来。
- 这一步**先进池，不排序**。排序是第 05 站的事，现在排会把还没想清的方案过早锁死。
- 动作是「做什么能解决问题」，可以带功能名了，但每条都要能指回一个问题。
- **每个问题至少列两种动作，其中一种不用 AI**：改流程、加模板、做培训、采购现成工具、简单软件。按 [AI四问.md](AI四问.md) 里的「AI 程度阶梯」从低往高想，第 05 站再比较。

### 2. 按字段登记

| 字段 | 写法 |
|---|---|
| 编号 | R01、R02… |
| 能力项名称 | 功能叫什么 |
| 业务痛点和目标 | 一句话：「现在怎样 → 做完怎样」 |
| 建设方向 | 增长 / 转化 / 留存 / 体验，选一个 |
| 需求来源 | 业务提需 / 产品自驱；写提出人或来源（访谈、数据、反馈） |
| 对应问题 | 指回第 01 站哪张问题定义卡 |
| 证据 | 证据标签 + 一句摘要 |
| 当前状态 | 调研 / 设计 / 开发 / 测试 / 已上线 / 迭代 / 下线 |

1→N 项目额外加两列：**承接团队**、**瓶颈团队负载**（重 / 中 / 轻：主要工作量是否落在最紧张的团队上）。

### 3. 跟着状态走

一条需求从立项一直往右走：立项 → 调研 → 设计 → 开发 → 测试 → 上线 → 迭代或下线。下线的需求留在池里，写下线原因，它是以后的反面证据。

## 进池门槛

**说得清重要性的需求才进池。** 进池就默认要做，只是排先后，所以门槛要卡住。

- 随便抽一条，都追得到出处。
- 说不清对应哪个问题的，不进池，放进「待澄清」，写清需要澄清什么。
- 描述过泛（如「体验优化」）的，拆开或关闭。

## 1→N 项目的额外步骤

- 已有需求池很长时，先读完，按第 01 站的问题归入专题。
- 每条标承接团队和瓶颈负载。
- 本期不纳入的需求单列一张表，按类型分组，每条写不纳入的理由（基础体验没过关、依赖未就位、与某需求重叠待合并、需先等某方拍板、属缺陷走常规流程等）。
- 已明确放弃的方向单独写一段，防止以后被反复提起。

## 自检清单（关卡）

- [ ] 每条需求都指回一个问题定义卡
- [ ] 每个问题至少有一个非 AI 的动作进池（哪怕最后不选它）
- [ ] 每条写了来源和证据标签
- [ ] 业务痛点和目标是一句话，「现在怎样 → 做完怎样」
- [ ] 没有在这一站排优先级（或者 1→N 项目里原池的优先级被标为「原池标注，待第 05 站重排」）
- [ ] 说不清重要性的需求已移入「待澄清」
- [ ] 1→N：每条有承接团队和瓶颈负载；不纳入的需求每条有理由
