# 第 05 站：跑评测与打分

**产物：** `评测方案.md` ④、`结果/<时间>/raw.jsonl`、`结果/<时间>/汇总.md`

## 1. 被测配置写清楚

在方案 ④ 里写：

- **提示词**：PRD v几 第四节原文（只把工具名换成可执行的名字），放在 `评测集/prompts/<环节>.md`。不为了评测另改一版；评测中发现要改，改完是新版本，要重跑。
- **工具**：几个、每个做什么；环节级评测用固定返回（见下）。
- **资料**：资料包几份。
- **被测模型**：候选模型表里选进来的，写模型名字符串和查价日期。
- **评审模型**：和被测模型不同厂商；只判断，不改写。

## 2. 文件格式

### models.json

```json
{
  "models": [
    {"name": "deepseek-chat", "base_url": "https://api.deepseek.com/v1", "model": "deepseek-chat",
     "key_env": "DEEPSEEK_API_KEY", "price_in": 2, "price_out": 8, "currency": "CNY"},
    {"name": "qwen-plus", "base_url": "https://dashscope.aliyuncs.com/compatible-mode/v1", "model": "qwen-plus",
     "key_env": "DASHSCOPE_API_KEY", "price_in": 0.8, "price_out": 2, "currency": "CNY"}
  ],
  "judge": "qwen-plus"
}
```

- 地址、模型名、单价**以候选模型表里查到的官方值为准**，上面只是格式示例。
- `price_in` / `price_out`：每百万 token 的价格。
- `key_env`：Key 所在的环境变量名。**Key 只放环境变量**，告诉用户在终端里 `export DEEPSEEK_API_KEY=...` 或写进不进仓库的 `.env` 再 `source`；不要让用户把 Key 发在对话里，发了也不要复述。
- 可选：`temperature`（默认 0.7，保持和线上一致）、`json_mode`（接口不支持 `response_format` 时设 `false`）、`timeout`、`extra`（厂商特有参数）。
- `judge`：评审模型的 `name`。评审模型也可以同时是候选，脚本会自动跳过「自己评自己」，那几题标「待人工」。

### cases.jsonl

一行一题：

```json
{"id": "T04", "stage": "正文", "type": "边界", "focus": ["参数"], "task": "写第四章 建设方案（资料里有 70 MPa、3.0 MPaG 两个干扰数）",
 "system": "prompts/正文.md",
 "vars": {"truth_base": {"validated_data": {"pressure_level": "35MPa"}}, "structure": {"current_chapter_index": 4}},
 "user": "请撰写第四章 建设方案。",
 "tools": {"internal_rag_tool": {"description": "检索项目资料", "returns": {"match": [{"if_contains": "压力", "return": "……资料原文片段……"}], "default": "未检索到相关资料"}}},
 "checks": [
   {"type": "contains", "value": "35 MPa", "label": "一期 35 MPa"},
   {"type": "not_regex", "pattern": "一期[^。]{0,20}70 ?MPa", "label": "没把 70 MPa 写成一期", "redline": true},
   {"type": "tool_called", "name": "internal_rag_tool", "label": "写前检索"}
 ],
 "judge": "70 MPa 只能作为远期预留出现；3.0 MPaG 是电解槽出口压力，不能当加注压力。"}
```

| 字段 | 说明 |
|---|---|
| `id` `user` | 必填。`user` 也可以用 `{{}}` 引用 vars |
| `system` / `system_text` | 提示词文件（相对评测集目录）或直接写文本 |
| `vars` | 提示词里 `{{区块.字段}}` 的值；可以写嵌套对象，也可以写平铺的 `"truth_base.validated_data": "..."` |
| `tools` | 工具名 → 描述、参数（JSON Schema，可省）、固定返回。`returns` 可以是一段文本，或按参数里的关键词匹配返回 |
| `response_format` | 写 `"json"` 时请求 JSON 模式 |
| `checks` | 代码判定，见下表；`redline: true` 的没过就记红线 |
| `judge` | 评审模型的评分标准；只在代码判不了时用 |
| `runs` | 这题跑几次，默认 3 |

检查类型：

| type | 参数 | 判什么 |
|---|---|---|
| `contains` / `not_contains` | `value` | 包含 / 不含某段文字 |
| `contains_any` / `contains_all` / `not_contains_any` | `values` | 等价写法任一 / 全部 / 都不能出现。数字的等价写法（2.5 亿、25,000 万元）用 `contains_any` |
| `regex` / `not_regex` | `pattern` | 正则 |
| `count` | `value`、`min`、`max` | 某段文字出现次数，如「[待补充」至少 1 次 |
| `min_chars` / `max_chars` | `value` | 字数 |
| `json_valid` | — | 输出是合法 JSON |
| `json_path_equals` | `path`、`value` | 如 `audit_status` = `FAIL` |
| `json_sum` | `path`、`equals` | 如 `full_outline[*].suggested_words` 之和 = 12000 |
| `tool_called` / `tool_not_called` | `name` | 过程检查：调没调某个工具 |

## 3. 判定顺序

1. **能用代码判的先用代码判**：数字对不对、作废的数字出没出现、各部分加起来对不对、待补充标记有几处、调了哪些工具。
2. **剩下的交给评审模型**，按 `judge` 里的标准判；评审模型和被测模型不是同一个。
3. **人工抽检**：每个模型至少抽 20% 的「过」和全部「待人工」，业务专家逐条看。人工推翻了评审模型的，记进报告，并考虑把那条标准写得更具体或改成代码判定。

## 4. 每题跑三次

每次都是全新会话（脚本每次重新发请求，不带上次的对话），三次都过才算过。只过一两次的题，报告里单独列为「不稳定」：它说明提示词或模型在这里靠运气。

## 5. 跑的顺序

1. `--dry-run`：格式、渲染、Key 都没问题。
2. 先用 1 个候选、`--runs 1` 跑全部题，看题目和检查本身有没有写错（检查写错比模型错更常见）。
3. 再跑全部候选、`--runs 3`。跑之前告诉用户预计花多少钱：题数 × 候选数 × 3 × 每题成本【测算】。
