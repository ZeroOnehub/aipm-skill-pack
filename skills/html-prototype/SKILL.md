# HTML 原型

> 改编自 [plannotator/effective-html](https://github.com/plannotator/effective-html) 的 `html-prototype`（MIT，plannotator）。改动：中文化；去掉「只能被显式调用」的限制；去掉对仓库内 design-artifact skill 的依赖；加入 AI 功能的状态清单；产出物默认存进拾阶的原型目录。

为一个产品决策做一个可信的模型。按用户的语境定样式，不套一成不变的「家装风格」。目标不是把每一屏都做出来，而是让关键的视觉问题或行为问题**可以被检验**。

## 选保真度

二选一：
- **视觉稿（Mockup）**：问题在视觉层级、布局、字体、颜色、产品调性时，做精致、响应式、基本静态的稿子。
- **交互原型（Prototype）**：问题在导航、输入、状态变化、反馈、出错恢复、转场时，做一条能走通的流程。

不要为了显得完整给视觉稿硬加交互。用户两个都要时，保持同样的内容和结构，方便对比保真度的变化。

## 从语境推导方向

动手前看对话、提供的参考和项目里的东西：设计规范、设计 token、已有组件、产品截图、附近的产物。在拾阶里，先读 `02-PRD/PRD.md` 和 `03-原型交互/` 里已有的线框图。

依据的优先级：
1. 用户明确的视觉和功能要求；
2. 项目已有的设计语言和交互习惯；
3. 产品、受众、内容和场景；
4. 你自己的设计判断。

编码前定好：
- 用户和最关键的任务；
- 评审的场景边界；
- 视觉稿还是交互原型；
- 视觉方向的出处；
- 相关的状态模型；
- 真实产品从哪里开始接手。

没有设计系统时，从主题和场景里提炼一个具体的方向。别默认用渐变、深色仪表盘、千篇一律的卡片和装饰性数字。现场工具、编辑工作流、财务审批的原型不该长得一样。

## 只做一段可信的体验

选能回答评审问题的最小流程。名字、日期、状态、数量和文案都用真实且前后一致的。
- 建模范围内的导航要能用。
- 表单要有标签、校验、提交反馈和合理默认值。
- 只在中断或确认本来就是场景一部分时才用弹窗。
- 转场用来交代连续性和状态变化，不当装饰。
- 删掉没反应的按钮。属于真实系统的操作，说明边界，不要假装完成了。

## 把相关状态画出来

动手前先列状态，只画场景真能走到的：
- 加载中；
- 空状态；
- 出错；
- 成功；
- 禁用；
- 手机端；
- 需求里特有的状态。

**AI 功能额外考虑**：生成中（流式输出或进度）、生成失败可重试、结果需要人确认、低置信度提示、引用来源可展开、用户中途停止。这些状态通常就是 PRD 里「AI 能力边界」的落地。

看起来是异步的操作，一般要有加载、成功、失败或恢复；列表一般要考虑空状态；被禁用的操作要说明为什么。别为了凑清单把无关状态塞进主流程。没画的状态在交接时写明。

## 交互要完整

- 原生元素语义合适时就用原生元素。
- 整条建模流程能只用键盘走完。
- 焦点始终可见，重要转场后有意识地放置焦点。
- 弹窗要有可访问的名字、焦点锁定在弹窗内、按 `Esc` 关闭、关闭后焦点回到触发按钮。
- 表单错误和对应控件关联，重要状态变化要播报。
- 关键行为不能只藏在悬停里。
- 尊重 `prefers-reduced-motion`，同时保留状态反馈。
- 触控目标够大，页面不出现意外的横向滚动。

视觉稿模式下，控件可以不接线，但语义结构和焦点样式要保留，并说清这是静态评审稿。

## 交付约定

- 一个自包含的 `.html` 文件，必要的 CSS 和 JS 都内联。
- 不需要构建工具、登录、真实接口或外部服务。
- 用真正的响应式布局，不是把桌面画布缩小。
- 设计 token 少而具体，贴合选定的方向。
- 对比度达标，状态不只靠颜色区分。
- 宁可把一条流程做深做对，也不要做一个铺得很广的假产品。

## 检查和交接

在宽屏桌面和窄屏手机下测试，走一遍每个状态和控件。测 `Tab`、`Shift+Tab`、`Enter`、`空格`、需要时的方向键，弹窗的 `Esc`。检查控制台报错、页面溢出、超长内容、禁用行为、焦点归还和减少动效模式。

逐个检查每块不同底色区域上文字的实际前景色和背景色，尤其是在深色或有色区域里继承了 body 颜色的文字。没有浏览器工具时，说清哪些视觉和交互检查没做，不拿读源码代替。

交接时给出：文件的绝对路径、保真度、建模的场景、实现了的状态、刻意没做的生产行为。

## 产出位置

在拾阶里存到当前项目的 `03-原型交互/`，文件名如 `原型-<流程名>.html`，并在回复里说明它对应 PRD 的哪几条用户故事。
