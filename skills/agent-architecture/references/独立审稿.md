# 独立审稿

架构方案写完后，另开一个上下文专门挑毛病。写方案的你已经被自己的思路带着走了，看不出自己的漏洞；审稿人只拿到 PRD 和方案，不知道你是怎么想的，才看得出哪里是脑补。

## 怎么开审稿人

用子代理工具（DeepSeek Harness 里是 `subagent`）开一个新的子代理，**不要用 fork**（fork 会带上你的整段上下文，就不独立了）。把下面这段任务交给它，替换尖括号里的路径：

```text
你是独立审稿人，不参与撰写。只读这两个文件，不要改任何文件：
- 需求：<项目根目录>/02-PRD/PRD.md
- 方案：<项目根目录>/04-AI方案设计/架构方案.md

按五条标准审查方案：
1. 无编造：方案里关于用户、目标、核心闭环、边界、约束的每句话，都要能在 PRD 里找到依据，或者已经标了「待确认」。
2. 六条落地标准都有对应设计：可运行（一条命令能起，密钥放在代码外）、可容错（工具失败、模型幻觉、超时、越权都有降级）、可观测（日志、指标、轨迹）、可测试（核心流程和工具有自动测试，权限有边界测试）、可部署（部署形态和启动方式明确）、可度量（PRD 的每个指标都能采集到）。
3. 工具清单和五要素一致：每个工具都能对应到五要素（工具、知识、观察、行动、权限）里的某一条，五要素里要求的动作都有工具承接。
4. 降级策略覆盖工具失败、模型幻觉、超时、越权四种，并且和 PRD 的「错了怎么兜」一致。
5. 组件选型的理由和特征依据一致；形态判断（单次调用 / 固定流水线 / Agent）有 PRD 原文依据。

只输出下面这个 JSON，不要别的文字：
{"ok": true 或 false, "score": 0 到 100 的整数, "issues": [{"section": "方案里的第几节", "problem": "问题是什么", "severity": "high 或 medium 或 low"}], "summary": "两三句话的总体评价"}
有 severity 为 high 的问题时，ok 必须是 false。
```

## 拿到结果以后

1. `ok` 为 true：把分数、summary 和 issues 写进方案的「独立审稿」一节，medium、low 的问题能顺手改的就改。
2. `ok` 为 false：**逐条**按 issues 改方案（high 必须改，medium 尽量改），改完再开一个**新的**子代理按同样的任务复审一次。只复审一次，不要来回循环。
3. 复审仍然 `ok: false`：方案状态写「待修订草稿」，没改掉的问题写进待确认清单，告诉用户哪几条还没过。
4. 审稿人说的不一定都对。你认为它判错的，在「独立审稿」一节里写「不采纳：理由」，不要悄悄忽略。

## 子代理用不了时

当前环境没有子代理工具，或者子代理报错：自己按上面五条标准逐条检查，这一节标题写「自审（未做独立审稿）」，不要写「审稿通过」。告诉用户可以开一个新会话，把上面那段任务发给它，拿到第二双眼睛。
