# AI 产品架构方案

## 两句总纲

- **只选需要的，不为完整而选。** 每个组件都要回答「没有它产品会怎样」，答不上来就不要。
- **能不用 Agent 就不用。** 流程固定、一次调用就能出结果的产品，做成 Agent 只会更慢、更贵、更难测。

## 开场：盘点输入

1. 定位项目（从总控进来时已知）。下文「方案目录」指 `<项目根目录>/04-AI方案设计/`。
2. 依次读：`02-PRD/PRD.md`（重点：功能清单、主流程、AI 能力边界、评测样例、指标、约束）、`01-立项/立项报告.md` 的 AI 四问、`05-评测/可行性小样/小样结论.md`（有就读）。没有 PRD 时，按下面「需求拆解」的 6 个维度直接问用户，一次最多 3 问。
3. `架构方案.md` 已存在：读它，问用户是改还是重做。

## 第一步：形态判断（必做，决定后面走哪条路）

逐条问 PRD 的主流程：**运行时要不要模型自己决定下一步做什么、做几步？**

| 形态 | 判断标准 | 例子 | 后面怎么走 |
|---|---|---|---|
| 单次调用 | 一次输入 → 一次模型调用 → 结构化输出，前后是普通代码 | 文案改写、分类打标 | 跳过组件选型，写「调用设计」 |
| 固定流水线 | 步骤固定，模型只在某几步里做判断或生成 | 解析需求 → 检索 → 排序 → 写理由 | 跳过组件选型，写「流水线设计」 |
| Agent | 步骤数和工具调用顺序要模型临场决定，或要多轮自主推进 | 帮用户查资料并整理报告、代码助手 | 走完整的组件选型 |

判断写进方案第 1 节，附依据（引用 PRD 原文）。拿不准时选更简单的那个，在待确认清单里写「如果出现 X 情况，需要升级成 Agent」。

**检索要不要上向量库**：知识是结构化字段（价格、标签、类目）且量不大，用条件筛选加模型排序；只有大量非结构化文档要按语义找时才上向量检索（评测时配合 `eval-rag`）。

## 第二步：模型与成本

| 项 | 写什么 |
|---|---|
| 主模型 | 候选一到两个，理由（效果、价格、国内可用、合规） |
| 单次任务 | 调用几次、每次输入输出大约多少 token、耗时多少 |
| 单次成本 | 按官方价格算，标【测算】并写口径；有可行性小样的实测数据就用实测 |
| 月成本 | 单次成本 × PRD 里的预计用量，给出上限和超限后的降级办法 |
| 时延 | 和 PRD 的时延要求对照；达不到就写流式、缓存、换小模型还是改需求 |
| 兜底模型 | 主模型失败或超时时用什么 |

价格会变：联网查当天的官方价格并附链接和日期；查不到就写「价格待核」。

## 第三步：需求拆解（Agent 形态必做；其他形态做前 4 行即可）

六个维度，每个写「结论 / 明确或待确认 / 出处」，PRD 没写的一律「待确认」，不脑补：

1. 目标：要完成什么，怎样算做成
2. 用户：谁在用、多频繁、同步还是异步
3. 核心闭环：一次完整的「输入 → AI 行为 → 交付物」
4. 交付物：文档、决策、操作还是别的
5. 边界：明确不能做的事
6. 约束：时延、并发、合规、成本、可用模型

## 第四步：组件选型（只有 Agent 形态做）

1. 回答 [references/组件与特征表.md](references/组件与特征表.md) 里的 14 个特征问题。每个只能答 `yes` / `no` / `later` / `unknown`，并写一句依据：
   - `yes`：PRD 明确需要，或闭环里必然包含（碰到隐私、身份、支付数据，敏感操作就是 yes）；
   - `later`：PRD 里有「二期」「以后」这类原文依据；没有原文依据不要写 later；
   - `no`：闭环已经写清楚，这个特征不在里面；
   - `unknown`：信息确实不够才用。单人、单次、同步的闭环已经写明时，定时、多 Agent 团队、插件生态这类特征判 `no`，不要判 `unknown`。
2. 写成 `方案目录/architecture-features.json`（格式见参考表），运行：

   ```bash
   python3 <本 skill 目录>/scripts/select_components.py "<方案目录>/architecture-features.json"
   ```

   把输出的表格原样贴进方案。**不手改选型结果**；你觉得规则选得不对，写进待确认清单（例如「s07 技能加载由 large_knowledge=yes 触发，但内容是结构化库，更适合做成检索工具」）。
3. 不能运行脚本时，按参考表里的规则手工推，并在方案里注明「未运行选型脚本」。

## 第五步：架构设计

方案按 [templates/架构方案.md](templates/架构方案.md) 写，必含：

1. **架构图**：Agent 形态画七层架构（交互、产品、编排、模型、能力集成、数据、基础设施），Mermaid `flowchart`，**每个节点的文字不超过 20 个字**，细节放下面的表格里；流水线和单次调用形态画步骤图。
2. **工具清单**：名称、输入、输出、副作用、权限（允许 / 需确认 / 禁止）、属于哪一层。数据检索类工具属于能力集成层，不属于模型层。
3. **降级策略**：至少覆盖工具失败、模型幻觉、超时、越权四种，每条写「场景 → 怎么处理 → 用户看到什么」，要和 PRD 的「错了怎么兜」一致。
4. **可观测**：要记哪些日志、看哪些指标、轨迹怎么存；PRD 里的每个指标要能对应到一个埋点或日志来源，对应不上的写进待确认。
5. **上下文与记忆**：会话内带多少资料，跨会话记什么、不记什么。
6. **部署形态**：单进程、服务还是多 Agent；用什么语言；模型从哪来。

## 第六步：自审与待确认

1. 按参考表的「六条落地标准」逐条打 ✓ / ✗：可运行、可容错、可观测、可测试、可部署、可度量。
2. 检查有没有编造：方案里关于用户、目标、闭环、边界、约束的每句话，都要能在 PRD 里找到出处，或者已标「待确认」。
3. 这是你自己审，不是独立审稿，方案里写「自审」，不要写「审稿通过」。用户想要第二双眼睛，建议开一个新会话专门挑这份方案的毛病，或者拿去和研发评审。
4. **待确认清单**写进方案末尾。会改变范围、成本、安全、隐私的问题，同时写进 `aipm.json` 的 `pending`（`kind: decision`，`stage: ai-design`，`source` 指向 `04-AI方案设计/架构方案.md`），一次不超过 5 个；其余用默认值并写明理由。

## 收尾

- 告诉用户方案路径，用三行说：什么形态、每月大概多少钱、最大的一个风险。
- 更新 `aipm.json`：04 阶段第 01 站「架构方案」记 `passed`；有待确认项还没回答时记 `passed_pending`，`note` 写还差哪几条。
- 下一站是系统提示词（`system-prompt-design`），然后是研发交接（`build-launch`）。

## 红线

1. 没做形态判断就开始选组件。
2. 手改规则脚本的选型结果，或者为了「架构完整」多加组件。
3. 把【测算】的成本写成事实，或者价格不附来源和日期。
4. 降级策略缺工具失败、幻觉、超时、越权中的任何一种。
5. 自审写成「独立审稿通过」。
