# AI 产品架构方案

## 两句总纲

- **只选需要的，不为完整而选。** 每个组件都要回答「没有它产品会怎样」，答不上来就不要。
- **能不用 Agent 就不用。** 流程固定、一次调用就能出结果的产品，做成 Agent 只会更慢、更贵、更难测。

## 开场：盘点输入

1. 定位项目（从总控进来时已知）。下文「方案目录」指 `<项目根目录>/04-AI方案设计/`，「本 skill 目录」指这份 SKILL.md 所在的文件夹。
2. 依次读：`02-PRD/PRD.md`（重点：功能清单、主流程、AI 能力边界和下面的「Agent 特征判断」表、评测样例、指标、约束）、`01-立项/立项报告.md` 的 AI 四问、`05-评测/可行性小样/小样结论.md`（有就读）。没有 PRD 时，按下面「需求拆解」的 6 个维度直接问用户，一次最多 3 问。
3. `架构方案.md` 已存在：读它，问用户是**改**（小修）、**重做**，还是**升版**（PRD 改了或加了新需求）。升版走文末「升版模式」。

## 第一步：形态判断（必做，决定后面走哪条路）

逐条问 PRD 的主流程：**运行时要不要模型自己决定下一步做什么、做几步？**

| 形态 | 判断标准 | 例子 | 后面怎么走 |
|---|---|---|---|
| 单次调用 | 一次输入 → 一次模型调用 → 结构化输出，前后是普通代码 | 文案改写、分类打标 | 跳过组件选型，写「调用设计」 |
| 固定流水线 | 步骤固定，模型只在某几步里做判断或生成 | 解析需求 → 检索 → 排序 → 写理由 | 跳过组件选型，写「流水线设计」 |
| Agent | 步骤数和工具调用顺序要模型临场决定，或要多轮自主推进 | 帮用户查资料并整理报告、代码助手 | 走完整的组件选型 |

判断写进方案第 1 节，附依据（引用 PRD 原文）。PRD 的特征表里 `fixed_orchestration` 判「需要」、`multi_step` 判「不需要」时，多半是固定流水线。拿不准时选更简单的那个，在待确认清单里写「如果出现 X 情况，需要升级成 Agent」。

**检索要不要上向量库**：知识是结构化字段（价格、标签、类目）且量不大，用条件筛选加模型排序；只有大量非结构化文档要按语义找时才上向量检索（评测时配合 `eval-rag`）。

## 第二步：模型与成本

| 项 | 写什么 |
|---|---|
| 主模型 | 候选一到两个，理由（效果、价格、国内可用、合规） |
| 单次任务 | 调用几次、每次输入输出大约多少 token、耗时多少 |
| 单次成本 | 按官方价格算，标【测算】并写口径；有可行性小样的实测数据就用实测 |
| 月成本 | 单次成本 × PRD 里的预计用量，给出上限和超限后的降级办法 |
| 时延 | 和 PRD 的时延要求对照；达不到就写流式、缓存、换小模型还是改需求 |
| 兜底模型 | 主模型失败或超时时用什么 |

价格会变：联网查当天的官方价格并附链接和日期；查不到就写「价格待核」。

## 第三步：需求拆解（Agent 形态必做；其他形态做前 4 行即可）

六个维度，每个写「结论 / 明确或待确认 / 出处」，PRD 没写的一律「待确认」，不脑补：

1. 目标：要完成什么，怎样算做成
2. 用户：谁在用、多频繁、同步还是异步
3. 核心闭环：一次完整的「输入 → AI 行为 → 交付物」
4. 交付物：文档、决策、操作还是别的
5. 边界：明确不能做的事
6. 约束：时延、并发、合规、成本、可用模型

## 第四步：五要素（所有形态都做）

把需求落进五个槽位，这张表就是产品的领域骨架，后面的工具清单要逐条对得上：

| 要素 | 问题 | 写什么 |
|---|---|---|
| 工具 | 交付物需要什么外部动作？ | 查询、写入、调用、发送，各自对哪个系统 |
| 知识 | 领域专长从哪来？ | 文档、数据表、业务规则、风格指南，谁维护、多久更新 |
| 观察 | 怎么确认动作产生了预期效果？ | 返回状态、校验结果、日志、用户反馈 |
| 行动 | 动作以什么形式执行？ | 接口调用、页面操作、消息、文件 |
| 权限 | 哪些动作要审批，哪些数据不能碰？ | 需确认的动作、禁止的动作、不能送进模型的数据 |

单次调用形态可以只写工具和知识两行，其余写「无」。

## 第五步：组件选型（只有 Agent 形态做）

1. **PRD 有「Agent 特征判断」表**（第 02 阶段 prd 第 04 站写的）：直接转换，不要重新判一遍：

   ```bash
   python3 <本 skill 目录>/scripts/features_from_prd.py "<项目根目录>/02-PRD/PRD.md" -o "<方案目录>/architecture-features.json"
   ```

   脚本提示有缺行、判断词不认识的，按提示补。你从架构角度认为某一行判错了，**不要悄悄改**：写进待确认清单（「`large_knowledge` 表里判需要，但内容是 300 条结构化数据，建议改成不需要，s07 换成一个检索工具」），用户同意后，PRD 的特征表和 json 一起改，PRD 已成稿的按 prd 的升版规则走。
2. **PRD 没有特征表**：按 [references/组件与特征表.md](references/组件与特征表.md) 自己回答 14 个特征问题，每个只能答 `yes` / `no` / `later` / `unknown`，写一句依据：
   - `yes`：PRD 明确需要，或闭环里必然包含（碰到隐私、身份、支付数据，敏感操作就是 yes）；
   - `later`：PRD 里有「二期」「以后」这类原文依据；没有原文依据不要写 later；
   - `no`：闭环已经写清楚，这个特征不在里面；
   - `unknown`：信息确实不够才用。单人、单次、同步的闭环已经写明时，定时、多 Agent 团队、插件生态这类特征判 `no`，不要判 `unknown`。

   写成 `方案目录/architecture-features.json`（格式见参考表），并建议用户回 PRD 第 04 站补上特征表。
3. 运行选型脚本，把输出的表格原样贴进方案。**不手改选型结果**：

   ```bash
   python3 <本 skill 目录>/scripts/select_components.py "<方案目录>/architecture-features.json"
   ```

4. 不能运行脚本时，按参考表里的规则手工推，并在方案里注明「未运行选型脚本」。

**单次调用和固定流水线**也要看特征表：判「需要」的特征在流程里要有落点，写进方案第 5 节「特征落点」。例如 `audit_needed` → 输出前的拦截与留痕步骤，`destructive_ops` → 动作前的用户确认，`cross_session_memory` → 存什么、存多久。

## 第六步：架构设计

方案按 [templates/架构方案.md](templates/架构方案.md) 写，必含：

1. **架构图**：Agent 形态画七层架构（交互、产品、编排、模型、能力集成、数据、基础设施），Mermaid `flowchart`，**每个节点的文字不超过 20 个字**，细节放下面的表格里；流水线和单次调用形态画步骤图。
2. **工具清单**：名称、输入、输出、副作用、权限（允许 / 需确认 / 禁止）、属于哪一层、对应五要素的哪一条。数据检索类工具属于能力集成层，不属于模型层。
3. **降级策略**：至少覆盖工具失败、模型幻觉、超时、越权四种，每条写「场景 → 怎么处理 → 用户看到什么」，要和 PRD 的「错了怎么兜」一致。
4. **可观测**：要记哪些日志、看哪些指标、轨迹怎么存；PRD 里的每个指标要能对应到一个埋点或日志来源，对应不上的写进待确认。
5. **上下文与记忆**：会话内带多少资料，跨会话记什么、不记什么。
6. **部署形态**：单进程、服务还是多 Agent；用什么语言；模型从哪来。

写完按参考表的「六条落地标准」逐条打 ✓ / ✗：可运行、可容错、可观测、可测试、可部署、可度量。

## 第七步：独立审稿

按 [references/独立审稿.md](references/独立审稿.md) 开一个**新的子代理**（不是 fork）当审稿人，只给它 PRD 和方案两个文件。不通过就逐条改，再开一个新子代理复审一次；复审还不过，方案状态写「待修订草稿」，没改掉的问题进待确认清单。子代理用不了时自己按同样的标准审，标题写「自审（未做独立审稿）」。

## 第八步：待确认清单（分两类）

把需求拆解、五要素、选型、审稿里冒出来的问题合到一起，去掉重复的（说法不同、问的是同一件事的只留一条），再分两类写进方案末尾：

| 类 | 是什么 | 怎么写 | 去哪 |
|---|---|---|---|
| 你来答 | 产品经理能回答的：给谁用、要做到什么、不要什么、愿意花多少钱和时间、内容和规则从哪来、出了问题希望怎么处理 | 大白话，不用术语，原问题里塞了几个小问的只留最关键的一两个，可以带一个回答示例，不超过 80 字；标优先级：1 = 不答就没法动手或方案要大改，2 = 重要但可以先按常见做法走，3 = 细节 | 优先级 1 的写进 `aipm.json` 的 `pending`（`kind: decision`，`stage: ai-design`，`recommend` 写推荐和一句理由，`source` 指向 `04-AI方案设计/架构方案.md`），同时开着的不超过 5 个 |
| 研发判断 | 只有工程师能判断的事，或者对方案的技术备注（模型和服务怎么选、字段、实现路径） | 一句话，不超过 60 字 | 不进待处理；研发交接时原样带进交接包，交给编码 AI 或研发判断 |

拿不准算哪一类时，算「你来答」。

## 收尾

- 告诉用户方案路径，用三行说：什么形态、每月大概多少钱、最大的一个风险；再说审稿结果（通过 / 改后通过 / 待修订）。
- 更新 `aipm.json`：04 阶段第 01 站「架构方案」记 `passed`；有「你来答」的问题还没回答时记 `passed_pending`，`note` 写还差哪几条。
- 下一站是系统提示词（`system-prompt-design`），然后是研发交接（`build-launch`）。选中的组件说明和参考代码在 [references/components/](references/components/)，研发交接时会按选型复制进交接包，这里不用复制。

## 升版模式（PRD 改了或加了新需求）

做产品最常见的坑：有了新想法直接改代码，PRD、方案和代码从此对不上。所以新需求先落回 PRD，再升版方案，最后才改代码。

1. **先看 PRD。** 新需求还没写进 PRD 的，先让用户走 prd 的升版（PRD 存历史版、升版本号、特征表只重判相关的行）。不要只凭口头需求改方案。
2. **存档。** 把当前的 `架构方案.md`、`architecture-features.json` 复制进 `方案目录/历史/`，文件名加版本号：`架构方案-v<N>.md`、`architecture-features-v<N>.json`。
3. **只重判受影响的特征。** 从 14 个特征里挑出和新需求直接相关的（新需求没提到、也推不出来的不挑；拿不准的挑上），只重判这几个，其余沿用上一版的判断和依据。这样同一份需求不会因为重判而无端改选型。PRD 特征表已经更新的，直接重新转换即可。
4. **对比选型。**

   ```bash
   python3 <本 skill 目录>/scripts/diff_components.py "<方案目录>/历史/architecture-features-v<N>.json" "<方案目录>/architecture-features.json"
   ```

   输出的「选型变化」表原样贴进方案的「版本记录」一节，每条带骨架待办。
5. **只改受影响的章节**：架构图、工具清单、降级、可观测里和变化有关的部分；改过的段落标「v<N+1> 修改」。改完照样做第七步独立审稿和第八步待确认。
6. **记一笔迭代记录**：在 `方案目录/迭代记录.md` 末尾追加一条（不存在就新建）：

   ```markdown
   ## <日期> · v<N+1> · <新需求一句话>
   - PRD：v<旧> → v<新>
   - 重新判断：<特征 id 列表>；其余沿用 v<N>
   - 选型变化：<s12 放弃 → 必选；没有就写「无」>
   - 骨架待办：<按 参考组件/s12_cron_scheduler/README.md 补 s12；没有就写「无」>
   - 人工验证结论：（由用户填，AI 不替写）
   ```

7. **已经在开发的**（`aipm.json` 里有 `build`）：告诉用户下一步走 `build-launch` 的「同步交接」，把新版 PRD、方案和新增组件的参考代码送进代码文件夹，编码 AI 按骨架待办增量修改，不要整体重写。

## 红线

1. 没做形态判断就开始选组件。
2. 手改规则脚本的选型结果，或者为了「架构完整」多加组件。
3. PRD 有特征表还自己重判一遍，或者悄悄改特征表的判断。
4. 把【测算】的成本写成事实，或者价格不附来源和日期。
5. 降级策略缺工具失败、幻觉、超时、越权中的任何一种。
6. 没开子代理审稿却写「审稿通过」；用 fork 当独立审稿。
7. 升版时把 14 个特征全部重判，或者不留上一版就覆盖。
